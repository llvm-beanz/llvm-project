# Initial Guidelines

Please make sure that your changes are appropriately tested with unit tests
covering each phase of translation in the compiler, and that your changes
conform to the [LLVM Coding Standards](llvm/docs/CodingStandards.rst).

Also please review the feme/.instructions.md file.

When you build and test ensure that you are using object file caching, and
building with assertions enabled. Also build and test the `check-feme` target
ensuring that all the target dependencies are correctly setup so that the test
dependencies will build before running the tests.

When you deviate from the design document please update the design document.

Also please run the Vulkan CTS from the checkout under /home/dev/dev/VK-GL-CTS/
after each change and update the VulkanCTSReport.md. Please keep the
Vulkan14FeatureInventory and VulkanExtensionInventory up to date with each
change as well.

If the request is to complete a roadmap stage, if you complete it please strike
it through on the roadmap document, if you do not, please add entries to the
roadmap document to break down the remaining work for that milestone.

During the H6 milestone breakdowns things have gone a little crazy with nesting
letters in strange ways. Please avoid nesting milestones more than one lowercase
letter deep going forward (i.e. Q54(a)).

The offload-test-suite checked out at /home/dev/dev/offload-test-suite has a
branch named feme on the remote at
https://github.com/llvm-beanz/offload-test-suite.git, which adds a generated set
of targets to run the tests against the feme ICD (check-hlsl-feme-vk).

Break your changes into small code changes with each change committed
spearately. Record your thought process into a file named "agent_thoughts.md" at
the root of the repository, appending to the file under a new top-level heading
if it already exists, and commit it in its own commit when you're done.

# Request

Can you close out L72(a) from the roadmap or other prerequisites blocking the
L-series milestones?

> **340 `dEQP-VK.glsl.texture_functions.*_compute` CTS cases fail SPIR-V import
> outright with `"unhandled opcode <N>"` for five distinct opcodes MLIR's own
> SPIR-V dialect has zero enum/Op-class coverage for at all** --
> `OpImageSampleProjExplicitLod` (92, 240 cases),
> `OpImageSampleProjDrefExplicitLod` (94, 24 cases), `OpImageQuerySizeLod` (103,
> 34 cases), `OpImageQueryLevels` (106, 34 cases, directly correlated with the
> CTS `query.texturequerylevels.*` group), and `OpImageQuerySamples` (107, 8
> cases) -- confirmed via roadmap L72's own real IR reduction: MLIR's
> autogenerated deserializer (`mlir/tools/mlir-tblgen/SPIRVUtilsGen.cpp`) only
> emits this bare-opcode-number form when `spirv::stringifyOpcode(N)` returns
> empty, i.e. `SPIRVBase.td` has no enum case at all for `N` -- a stronger
> signal than "recognized but unimplemented" (which would instead say
> `"unhandled deserialization of <Name>"`). This is a genuine **upstream MLIR**
> gap, not a feme bug: fixing it needs adding real TableGen op definitions
> (`SPIRVImageOps.td`, mirroring the existing
> `ImageQuerySizeOp`/`ImageSampleProjDrefImplicitLodOp` neighbors) plus
> serialization/deserialization/verifier support for all five opcodes in MLIR's
> own SPIR-V dialect -- a materially larger, cross-repository, riskier
> undertaking than any other row in this project's history, deliberately not
> attempted in this row. Not yet started; needs its own scoping decision
> (upstream MLIR contribution vs. a feme-local pre-import SPIR-V rewrite of
> these five opcodes into an already-supported equivalent form) before
> implementation can begin.
