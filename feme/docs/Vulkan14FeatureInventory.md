# Vulkan core mandatory-feature/limit/extension inventory

Originally roadmap D1's 1.3/1.4 checklist ("An accurate 1.3/1.4
mandatory-feature/limit/extension inventory", see [Roadmap.md](Roadmap.md)
&sect;1.9.2); now the whole-core version of the same thing, because the
declared scope is full Vulkan 1.4 conformance covering compute, graphics
and ray tracing ([FeMeVulkanDesign.md](FeMeVulkanDesign.md)'s "Conformance
Target"), and a 1.4 claim carries every earlier core version's surface too.

It is generated by `feme/utils/vk_gen_feature_inventory.py` from
Vulkan-Headers' `vk.xml` directly (the same way `vk_gen_entrypoints.py`
already resolves its own `CORE_FEATURES` transitively) rather than
re-derived by hand the way roadmap C6 did for Vulkan 1.2's much shorter
list. It enumerates, for each core version:

- every **feature** member of that version's feature struct --
  `VkPhysicalDeviceFeatures` for 1.0, `VkPhysicalDeviceVulkan1xFeatures`
  for 1.1 onward. The "Advertised" column is what this ICD reports
  `VK_TRUE` today, in *both* the aggregate struct and any dedicated
  pre-promotion struct (the two disagreeing is what
  `dEQP-VK.api.info.*.feature_extensions_consistency` catches).
- every **limit** member of that version's properties struct (1.3/1.4
  only, see the scope note below) -- enumerated, not judged: a limit's
  truthfulness is about its numeric value, not its name, so "Advertised"
  is always `n/a` for a limit row.
- every **extension** `vk.xml` records as `promotedto` that version --
  the mandatory extension floor. "Advertised" here means *implemented*:
  either advertised by name in `getSupportedDeviceExtensions`, or
  reachable through the promoted core `VK_VERSION_1_x` entry points
  alone, which is equally sufficient for the version's own floor. Rows of
  the second kind say "core, not advertised by name" in their note;
  [VulkanExtensionInventory.md](VulkanExtensionInventory.md) is where that
  distinction is tracked per extension.

**Scope note on limits.** 1.0's ~110 `VkPhysicalDeviceLimits` fields and
1.1/1.2's properties-struct fields are omitted deliberately (the
`:feature,extension` category filter in the command below): every one of
them is already written and cross-checked by
`dEQP-VK.api.info.vulkan1p1`/`vulkan1p2`, unlike 1.3/1.4's, which roadmap
E2 had to add from nothing. Regenerate with them included if that ever
stops being true.

To regenerate this file after a `PhysicalDeviceInfo.cpp`/
`EntryPoints.cpp`/`getSupportedDeviceExtensions` change, update
`feme/lib/Vulkan/AdvertisedPromoted{Features,Extensions}.txt` to match
and re-run:

```shell
python3 feme/utils/vk_gen_feature_inventory.py <path-to-vk.xml> \
    --version VK_VERSION_1_0:feature,extension \
    --version VK_VERSION_1_1:feature,extension \
    --version VK_VERSION_1_2:feature,extension \
    --version VK_VERSION_1_3 --version VK_VERSION_1_4 \
    --advertised-features feme/lib/Vulkan/AdvertisedPromotedFeatures.txt \
    --advertised-extensions feme/lib/Vulkan/AdvertisedPromotedExtensions.txt \
    -o feme/docs/Vulkan14FeatureInventory.md
```

(then re-add this intro section by hand -- the script only emits the
table below). Use the `vk.xml` from the VK-GL-CTS checkout under test
(`external/vulkan-docs/src/xml/vk.xml`), not the system one: the system
package is older, and this inventory only means something against the same
registry the CTS itself was built from.
