## Coding Standards

- Follow [LLVM Coding Standards](/llvm/docs/CodingStandards.md)
- Use clang-format on all changes before committing
- Break changes into as small granularity as possible where each change that isn't a non-functional refactoring is individually testable and tested.

## Language, Libraries & Standards

- Target C++17 and avoid vendor-specific extensions.
- For Python scripts, follow PEP 8.
- Prefer standard library or LLVM support libraries instead of reinventing data structures.

## Comments & Documentation

- Each source file should include the standard LLVM file header.
- Header files must have proper header guards.
- Non-trivial classes and public methods should have Doxygen documentation.
- Use `//` or `///` comments normally; avoid block comments unless necessary.
- Non-trivial code should have comments explaining what it does and why. Avoid comments that explain how it does it at a micro level.
- Focus on comments being concise and informative, avoid overly verbose explanations.

## Language & Compiler Issues

- Write portable code; wrap non-portable code in interfaces.
- Do not use RTTI or exceptions.
- Prefer C++-style casts over C-style casts.
- Do not use static constructors.
- Use `class` or `struct` consistently; `struct` only for all-public data.
- When then same class is declared or defined multiple times, make sure it's consistently done using either `class` or `struct`.

## Headers & Library Layering

- Include order: module header → local/private headers → project headers → system headers.
- Headers must compile standalone (include all dependencies).
- Maintain proper library layering; avoid circular dependencies.
- Include minimally; use forward declarations where possible.
- Keep internal headers private to modules.
- Use full namespace qualifiers for out-of-line definitions.

## Control Flow & Structure

- Prefer early exits over deep nesting.
- Do not use `else` after `return`, `continue`, `break`, or `goto`.
- Encapsulate loops that compute predicates into helper functions.

## General Guidelines

- Use `assert` liberally; prefer `llvm_unreachable` for unreachable states.
- Do not use `using namespace std;` in headers.
- Provide a virtual method anchor for classes defined in headers.
- Do not use default labels in fully covered switches over enumerations.
- Use range-based for loops wherever possible.
- Capture `end()` outside loops if not using range-based iteration.
- Including `<iostream>` is forbidded. Use LLVM’s `raw_ostream` instead.
- Don’t use `inline` when defining a function in a class definition.

## Microscopic Details

- Preserve existing style in modified code.
- Prefer pre-increment (`++i`) when value is unused.
- Use `private`, `protected`, or `public` keyword as appropriate to restrict class member visibility.
- Omit braces for single-statement `if`, `else`, `while`, `for` unless needed.

- This build directory is configured with `-DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON`.
  LLVM enables a shared `LLVMCore` PCH by default for Clang+`ccache`

  force-included (`-include-pch`) into every translation unit in the
  build, including feme's. This silently supplies headers (e.g.
  `llvm/IR/Instructions.h`, for `AtomicRMWInst`) that a feme source file
  uses but never actually `#include`s itself -- the file only fails to
  compile once PCH is off, or once built in a context (a different
  build directory, a standalone tool, a future LLVM refactor that drops
  something from the PCH's own header set) that doesn't force-include
  the same PCH. Keep this flag set; if a fresh build directory is ever
  created for this project, pass it again at configure time, or the next
  missing-include bug like this one goes undetected until it surfaces
  somewhere else, much more confusingly.

## Running `feme-vk` / offload-test-suite against the real driver

- **Build `check-hlsl-feme-vk` from this repo's own `build/` directory, not
  a new/separate build directory.** This project's own `build/` is
  already configured with `-DLLVM_ENABLE_PROJECTS="feme;mlir"
  -DLLVM_EXTERNAL_PROJECTS=OffloadTest
  -DLLVM_EXTERNAL_OFFLOADTEST_SOURCE_DIR=/home/dev/dev/offload-test-suite
  -DDXC_DIR=/usr/local/bin -DGOLDENIMAGE_DIR=/home/dev/dev/offload-golden-images`
  (confirm with `grep LLVM_EXTERNAL_PROJECTS build/CMakeCache.txt`), and
  `ninja -C build check-hlsl-feme-vk` builds/runs the whole suite
  incrementally in well under a minute, since LLVM/clang/mlir/feme are
  already built there with a warm `ccache`. Setting up a brand-new,
  separate build directory for this (as a prior session's roadmap `L192`
  did, at `/home/dev/dev/offload-test-suite/build`) re-triggers a full
  ~5,400-target, ~15-minute from-scratch build every session with `ccache`
  mostly missing -- not because `ccache` itself is broken, but because
  that separate directory's own CMake-generated headers/include paths
  differ from `build/`'s, so almost nothing from `build/`'s already-warm
  cache applies there. This is the real shape of the
  `LLVM_EXTERNAL_PROJECTS=OffloadTest` "cache-persistence gap" multiple
  prior sessions carried forward as an unstarted item: it was never a
  `ccache` bug to fix, just a build-directory choice to avoid. (That
  separate directory does not appear to persist across sessions either,
  compounding the cost -- one more reason to prefer the main `build/`.)
- **`/home/dev/dev/offload-test-suite`'s local `feme` branch is wiped back
  to a pure `origin/main` mirror before every single session, by design,
  not by accident.** `/opt/llvm-tooling/scripts/agent-setup.sh` (root-owned,
  not a git repo, outside this project's control, run automatically before
  each Copilot invocation per its own header comment) unconditionally does
  `git fetch --tags origin && git reset --hard origin/main && git pull
  --ff-only origin main` against this checkout (and `DirectXShaderCompiler`/
  `offload-golden-images`) to guarantee a clean, up-to-date auxiliary-repo
  state. This discards the FeMe-enabling CMake commit
  (`[Vulkan][FeMe] Add FeMe test targets`, upstream tip of
  `llvm-beanz/feme`, was `854cc3f`, now `0cc94c2` as of this session --
  **this hash moves over time as that branch gets rebased upstream; do
  not hardcode it, always resolve the current tip first**) every time.
  Multiple past sessions mistook this for a one-off regression and spent
  time "root-causing" it via `git reflog`/ancestry checks before finding
  this script -- it is expected, not a bug, and there is no write access
  to fix the trigger (root-owned script) or to persist the fix upstream
  (no push access to `llvm-beanz/offload-test-suite`). Treat "re-apply
  the cherry-pick" as a standard, every-session step, not an
  investigation: at session start, `cd /home/dev/dev/offload-test-suite

  single commit titled "[Vulkan][FeMe] Add FeMe test targets" as of this

  upstream either); re-apply `feme/offload-test-suite-patches/*.patch`
  (`git am`, in order) right after that cherry-pick every session -- see
  that directory's `README.md`.
- This container's system-wide `VK_ICD_FILENAMES` defaults to Mesa's
  `lvp_icd.json` (the `lavapipe` software driver), **not** this project's
  own `feme_vulkan` ICD. `offload-test-suite`'s own `lit.cfg.py` passes

- `check-hlsl-feme-vk`/`check-hlsl-clang-feme-vk`'s Pass/Fail counts are

  source changes at all. Confirm the right driver is selected with
  `vulkaninfo --summary | grep deviceName` (expect `FeMe CPU Vulkan
  Device`, not an Intel/AMD/Mesa name) before trusting any `feme-vk`
  Pass/Fail delta.
- Before trusting *any* VK-GL-CTS `deqp-vk` Pass/Fail count against this
  project's own ICD, rebuild `libfeme_vulkan.so` first (e.g. `ninja
  check-feme`, which already depends on it, or at minimum `ninja
  libfeme_vulkan.so`) -- do not assume a build directory's existing

  be 100% a stale-`.so` artifact -- a from-scratch rebuild immediately

  its 3 named groups (`subgroups`/`synchronization`/`synchronization2`)

- Always invoke `deqp-vk` with its own directory (e.g.
  `<build>/external/vulkancts/modules/vulkan`) as the working directory,
  never an arbitrary scratch directory. Many CTS cases (Amber script
  tests in particular, e.g. `subgroup_uniform_control_flow.discard.*`)

  current working directory (`./vulkan/amber/...`); running from the
  wrong directory produces a `ResourceError`/`Failed to open file` on
  those specific cases and can abort the whole run early, which looks
  exactly like a real crash but has nothing to do with this project's
  own driver at all.
- Never pipe `deqp-vk`'s stdout/stderr through a command that can close
  its read end early (e.g. `| head -N`, `| grep ... | head -N`). Once
  the downstream command exits, the kernel sends `deqp-vk` a `SIGPIPE`
  and kills it mid-test -- the truncated output that remains can look
  like a clean result (or worse, like leftover content from a *previous*
  run's `TestResults.qpa` in the same directory) and be misread as a
  real Pass/Fail, when the test never actually finished (roadmap H101:
  this exact mistake produced a false "workgroup_bad_stride correctness
  bug" investigation, and separately caused an *actual* crashing case to
  be misread as passing). Always redirect to a file first
  (`> out.log 2>&1`), then inspect the file afterward with `grep`/`tail`.
- As of `shaderFloat16` being enabled (roadmap L98(a)), a broad/blanket
  `dEQP-VK.spirv_assembly.*float16*` (or wider) sweep used to hit two
  known-crashing cases, `arithmetic_2.frexpstructe`/`arithmetic_2.frexpstructs`
  under `dEQP-VK.spirv_assembly.instruction.compute.float16` (aborting the
  whole `deqp-vk` process rather than failing cleanly) -- **fixed and
  CTS-verified, see roadmap L183**; both cases (and their `arithmetic_3`/

  Left here as a precedent: a naive per-case regex over a QPA log's own
  raw text can spuriously "find" a *different* test case's `Fail`/`Pass`
  status if it does not stop at that case's own `#endTestCaseResult`
  delimiter first -- always anchor a QPA-log scrape to that delimiter
  (see L183's own writeup for the investigation this once derailed).
- Any `feme-vk` case that compares its rendered output against a golden
  PNG (`imgdiff %t/Output.png %goldenimage_dir/...`, as opposed to a raw

## Dumping the IR an offload test actually feeds to the CPU pipeline

- When a `feme-vk` case fails inside a `feme-cpu-*` pass, the module that
  pass sees is *not* any file on disk: it is the result of importing the
  test's SPIR-V and running the earlier half of
  `feme::cpu::runPipeline`. Reconstructing it by hand from the HLSL (or
  from `dxc`'s own output) reliably produces a *different* CFG than the
  one that failed, and a triage built on that reconstruction can be
  entirely wrong.
- Set `FEME_DUMP_IR` in the environment to have `runPipeline` print the
  real module to stderr immediately before the wrapping stage, and run
  `offloader` directly on the artifacts lit already generated:

  ```
  VK_ICD_FILENAMES=<build>/tools/feme/tools/feme-vulkan/feme_icd.json \
  FEME_DUMP_IR=1 ./bin/offloader \
    tools/OffloadTest/test/feme-vk/<dir>/Output/<T>.test.tmp/pipeline.yaml \
    tools/OffloadTest/test/feme-vk/<dir>/Output/<T>.test.tmp.o \
    2>&1 | grep -v "^error:\|^gpu-exec:\|^Using\|^Command\|^Cleanup" > dump.ll
  ```

  The `.o` argument (the `dxc`-produced SPIR-V) is **required**; without
  it `offloader` reports `Pipeline description expects 1 shader(s) 0
  provided` and never reaches the pipeline. Run the case once under
  `llvm-lit -v --filter <name>` first so those `Output/` artifacts exist.
- The resulting `dump.ll` feeds straight into
  `./bin/feme-opt --llvm -passes=feme-cpu-wrap-entry -S dump.ll`, which
  turns a whole-driver failure into a seconds-long edit/debug loop. Note
  that this needs only `ninja feme-opt`, not a full ICD rebuild -- but
  **do** rebuild `feme-opt` before trusting any such run, for the same
  stale-binary reason the `libfeme_vulkan.so` warning above describes.
- `FEME_DUMP_IR` dumps too *late* to triage anything specific to a single
  `Normalize`-group pass (`SPIRVPushConstantLoweringPass`,
  `SPIRVResourceLoweringPass`, etc.): by that point SIMDization and wave
  lowering have already rewritten the module past recognition (e.g. a
  single vector load a pass like `SPIRVPushConstantLoweringPass` saw
  becomes several SIMD-lane-scalarized scalar loads by then). Set
  `FEME_DUMP_IR_PRENORM` instead to print the module immediately after
  `Normalize` finishes but before `checkSupportedRaisedOps` runs -- the
  exact shape those passes themselves operate on -- using the same
  `offloader` recipe above (only the environment variable name differs).
- Neither of the above pins down a `feme-cpu-simdize` diagnostic
  specifically: `FEME_DUMP_IR_PRENORM` predates `feme::cpu::LinearizePass`'s
  own control-flow rewriting entirely, and `FEME_DUMP_IR` postdates
  SIMDization. Set `FEME_DUMP_IR_PRESIMD` instead to print the module
  immediately after `LinearizePass` finishes but before `SIMDizePass`
  runs -- the exact shape `SIMDizePass` itself inspects (roadmap `L185`
  session).
- A "has a divergent branch" `feme-cpu-simdize` diagnostic names the
  function but not which block's terminator tripped it. Set
  `FEME_DUMP_DIVERGENT_BRANCH` to also print the offending block's name
  and terminator directly from `FunctionWidener::checkSupportedControlFlow`
  -- pairs well with `FEME_DUMP_IR_PRESIMD` (which shows the whole module
  the block name refers into) rather than replacing it (roadmap `L188`
  session).
- Manual CFG hand-tracing across pass-rewritten block names (comparing a
  `FEME_DUMP_IR_PRENORM`/`FEME_DUMP_IR_PRESIMD` dump against the actual
  state mid-`LinearizePass`) is error-prone: earlier passes rename/merge
  blocks (e.g. a `StructurizeCFG`-introduced `Flow4` can get folded into
  `Flow3.Flow4_crit_edge` by the time `LoopLinearizer::linearizeCycle`
  runs its own scans), so a dump taken at the wrong point shows different
  names than the ones a mid-pass diagnostic or scan actually sees. Set
  `FEME_DEBUG_L419H_TRACE` (gated, `errs()`-based tracing already wired
  into `LoopLinearizer::linearizeCycle`'s `RealExitCandidates` widening,
  roadmap `L419(h)` session) to print the *exact* candidate blocks/
  terminators that scan is examining and which ones it matches, in the
  pass's own current, post-earlier-rewrite naming -- this pinpointed a
  single-candidate, non-ambiguous false-positive match in one session
  after manual tracing had already failed once. The pattern (temporary,
  env-var-gated `errs()` instrumentation plus an empirical rebuild-and-run
  loop, rather than static reasoning about complex multi-pass
  interactions) generalizes well to any similarly tricky `Linearize.cpp`
  bug; add a new `FEME_DEBUG_<area>_TRACE` var the same way rather than
  reaching for `gdb` or hand-tracing first.

- `FEME_DUMP_IR_PRESIMD`/`FEME_DUMP_IR` are read via plain `::getenv()`
  inside whatever process actually calls it -- setting them via `cmake -E
  env ... llvm-lit ...` does **not** work, because lit's own
  `config.environment` is a curated whitelist, not a copy of the ambient
  shell environment (the same class of gap `FEME_VULKAN_SAFETY_NET_TIMEOUT_MS`
  hit, fixed in `offload-test-suite`'s own `lit.cfg.py`, see
  `feme/offload-test-suite-patches/`). For a one-off debug dump there is
  no need to patch lit's env passthrough for every such debug var: run
  the case once under `llvm-lit -v --filter <name>` so its `Output/`
  artifacts (`pipeline.yaml`, the `.o`, `source.hlsl`) exist on disk (they
  are **not** cleaned up after the test completes), then invoke
  `offloader` directly against them with the env var set in that command
  itself (see the recipe above) -- this bypasses lit's env curation
  entirely.
- Invoking `build/bin/clang-dxc` directly via the bash tool, with a real
  compile (not just `--version`), is blocked in this environment by a
  harness-level approval gate ("Permission denied... Copilot needed the
  user's approval and no one could answer"), even for a trivial one-line
  shader with no unusual flags -- this is not an OS/sandbox permission
  issue (plain file I/O and other bash commands work fine in the same
  session). The identical binary and flags succeed when `clang-dxc` is
  invoked as a subprocess *by* `llvm-lit` itself, so the restriction is
  specific to the bash tool's own direct-invocation path. Workaround:
  never re-invoke `clang-dxc` directly to regenerate a `.o` for
  debugging -- reuse the one an existing lit run already produced (see
  the previous bullet) and drive `offloader` directly instead, which is
  not blocked.

## Debugging a Release build with `gdb`

- The default build configuration is `CMAKE_BUILD_TYPE=Release`, which has
  no usable DWARF line/variable info: a `gdb` breakpoint on a `file:line`
  location pends forever and never hits, and `print <local-var>`/
  `info args` fail with "No symbol table info available" even at a
  breakpoint that *did* hit via a mangled function-name (not file:line)
  break -- confirmed via several failed attempts (roadmap `L184` session).
  Symbol-name breakpoints do work for confirming *which* pattern/function
  runs and how many times, using the demangled or mangled symbol.
- To inspect actual values (an `mlir::Type`/`Value`/instruction a pattern
  is matching against, say), the fastest reliable path is a temporary
  `llvm::errs() << ...` print added directly at the source line in
  question, followed by rebuilding only the smallest affected target
  (fast via `ccache`), rerunning the failing repro, and then deleting the
  print once the shape is understood. Don't reach for a full `Debug`
  reconfigure for a single investigation -- it invalidates the whole
  `ccache`-warmed object cache and the extra build time dwarfs the
  temporary-print loop's own cost.
- `gdb -batch -ex "bt full"` can hide a nondeterministic, timing-sensitive
  race entirely: confirmed (roadmap `L440`/`L441`) via a direct A/B test
  -- 1900 crash-loop iterations with `-ex "bt full"` enabled produced
  **zero** crashes, while the identical loop with plain `-ex bt` instead
  reproduced the same crash reliably (23/300). `bt full`'s extra
  per-frame local-variable printing apparently perturbs allocator/heap
  timing just enough to miss a use-after-free's narrow reuse window.
  Prefer plain `bt` for this class of bug; if deeper frame inspection is
  needed, use `-ex "frame N" -ex "info locals"` targeted at one specific
  frame instead of `bt full` on the whole stack.
- `FEME_DUMP_IR_PRELINEARIZE=1` (env var already in `Pipeline.cpp`) dumps
  the exact IR handed to `LinearizePass`, and is a much faster way to
  build a standalone `feme-opt --llvm -passes=feme-cpu-linearize` repro
  from a real, slow Vulkan-pipeline-driven crash than looping the whole
  `offloader`/CTS binary: capture the dump once from the real repro,
  then loop `feme-opt` alone under `gdb`+ASLR instead (confirmed,
  roadmap `L441`, to reproduce the same bug, including distinct crash
  signatures, in a fraction of the time). Other useful dump points in
  the same file: `FEME_DUMP_IR_PRENORM`, `FEME_DUMP_IR_ON_VERIFY_FAIL`,
  `FEME_DUMP_IR_PRESIMD`, `FEME_DUMP_IR`.
- **When a bug only reproduces through a specific real CTS test's own
  shader/dispatch shape** (confirmed, roadmap `L442`/`L446`, for a case
  needing a `glslang`-compiled GLSL shape -- like a dynamic
  `vec[i][j]`-style vector-component index -- that `dxc`-compiled HLSL
  could not faithfully replicate, since `dxc`'s codegen for that shape
  differs enough to trip an unrelated, already-known diagnostic instead):
  do not try to hand-build a new minimal HLSL/`dxc` repro from scratch.
  Instead, patch the real CTS test's own C++ (in the third-party
  `VK-GL-CTS` checkout, never committed to this repo) with an env-var-
  gated override that shrinks its dispatch/buffer-size parameters (e.g.
  workgroup size, loop trip counts) while reusing the exact same shader
  source and `glslang` compilation path as the real failing case. This
  keeps 100% codegen fidelity to the real bug while making each iteration
  a sub-second `deqp-vk --deqp-case=<one case>` run instead of the full,
  much larger real dispatch -- combine with the `FEME_DUMP_IR_*` dumps
  above to capture a small, fast, standalone `feme-opt` repro from the
  shrunk case. Revert the CTS-checkout patch once no longer needed (it is
  third-party source, not part of this project) but keep the technique
  and the exact env-var/parameter names in mind for reuse; neither
  `glslangValidator` nor `glslc` are built standalone in this environment,
  so this run-the-real-test-smaller approach is the only fast way to
  iterate on a `glslang`-specific codegen shape.


## Multi-day background CTS sweeps must be launched detached

- A full `dEQP-VK.*` re-triage (all ~3.25M cases via
  `feme/utils/run_vulkan_cts.py`) genuinely spans multiple sessions'
  worth of wall-clock time. The harness session's own background-process
  model terminates any attached background process (started without an
  explicit detach request) when that session ends -- it does **not**
  keep running into a future session just because it was started in a
  non-blocking way. A session that launches one of these sweeps attached
  and then ends will come back next time to find the process gone,
  mid-batch, with no final `report.txt` (confirmed: `L437` lost an
  in-flight sweep this way after ~199/1,808 batches).
- Launch any sweep intended to outlive the current session fully
  detached (e.g. `nohup ... &` inside a backgrounded invocation, launched
  so it is reparented away from the session's own process tree) so it
  survives independently of the harness session's lifetime, the same way
  a real multi-day CI job would. Verify immediately afterward with `ps
  aux` that the worker processes show a `?` controlling TTY (orphaned),
  not a TTY tied to the current shell.
- `run_vulkan_cts.py` has **no built-in `--resume`/checkpoint flag**. If
  a sweep is found dead with partial output (`qpa/*.qpa` present, no
  `report.txt`), do **not** assume the first N `qpa` files represent N
  fully-completed batches -- with `--workers W` concurrently-running
  batches, several files at both the front and back of the numeric
  sequence can be simultaneously partial when the process is killed (seen
  in `L437`: batches 194/195/197/198 were all partial, not just the very
  last one). The reliable way to compute genuinely-remaining work is to
  extract every actually-completed `CasePath="..."` from **all** `.qpa`
  files (regardless of which batch they belong to or whether that batch
  finished), subtract that set from the full case list, and re-launch a
  fresh sweep (new `--output-dir`, so the old partial batches aren't
  clobbered) against only the remainder. Treat the full re-triage's
  eventual results as the union of every such partial output directory's
  completed cases, not any single directory's own `report.txt` alone.

## `run_vulkan_cts.py --case-list` wants bare case names, not `--deqp-runmode` trie output

- `./deqp-vk -n '<pattern>' --deqp-runmode=txt-caselist` (the easiest way
  to turn a `-n` wildcard filter into a file for `run_vulkan_cts.py
  --case-list`) writes a full indented trie, with every line prefixed
  `GROUP: ` or `TEST: ` -- not the flat, one-case-per-line format
  `vk_cts_reconcile.py`'s own `read_case_list` expects (it strips
  comments/whitespace from each line and treats the rest as one literal
  test name verbatim, with no prefix stripping or group filtering at
  all). Feeding the raw trie file straight to `--case-list` fails fast
  and unhelpfully: `deqp-vk` reports `FATAL ERROR: Failed to initialize
  dEQP: Illegal character in test case name` for every batch (confirmed
  this way, `L452(a)`'s own CTS verification run). Filter to `^TEST: `
  lines and strip that prefix before use, e.g. `grep '^TEST: '
  trie.txt | sed 's/^TEST: //' > cases.txt`.
- Separately: a long-running process started with `nohup cmd &` inside a
  **synchronous** `bash` tool call does not survive that call returning --
  the whole session's process group is torn down once the sync call is
  marked complete, `nohup` notwithstanding (confirmed directly: a
  `run_vulkan_cts.py` sweep launched this way vanished with an empty
  `report.txt` showing 0 completed cases, long before the 70k-case sweep
  could possibly have finished). This is distinct from the "multi-day
  sweep needs full detach" guidance above, which is about surviving past
  the *end of the session*: for a sweep meant to finish *within* the
  current session (an hour or so, not days), simply invoke it with the
  bash tool's own `mode: "async"` (no `detach: true` needed) rather than
  backgrounding it with shell-level `&`/`nohup` inside a `sync`-mode call.

## `offload-test-suite` "drift" against `llvm-beanz/feme`: check content, not commit hashes

- `offload-test-suite`'s local `feme` branch is rebuilt by cherry-picking
  the FeMe-enabling change(s) from `llvm-beanz/feme` (see the "re-apply
  every session" note above) rather than fast-forwarding to that remote
  branch directly. A plain `git log local-feme..llvm-beanz/feme` /
  `git log llvm-beanz/feme..local-feme` ("N ahead / M behind") will
  therefore **always** show at least one "behind" commit even when the
  actual file content is fully in sync -- `git cherry-pick` produces a
  new commit object (different hash, often a different parent/tree
  checksum even when the author/date/message are copied verbatim), not a
  copy of the original commit.
- Before treating an apparent "behind" commit as real, undecided drift
  needing a rebase/reconciliation decision, compare it by **content**,
  not ancestry: `git show <remote-sha> | git patch-id` vs. `git show
  <local-equivalent-sha> | git patch-id`. Equal patch-ids mean the change
  is already fully present locally under a different hash -- there is
  nothing to reconcile, and no decision is actually pending. (Confirmed
  this session, `L439`: the single `0cc94c2` commit flagged as "drift"
  across many prior sessions is patch-id-identical to this repo's own
  `b606d08`, both titled "`[Vulkan][FeMe] Add FeMe test targets`", same
  author/date -- a false positive from hash-based ancestry checking, not
  real drift. No rebase was ever actually needed.)
- If a future `git fetch` surfaces more than the one already-known commit
  on `llvm-beanz/feme`, re-run this same patch-id comparison for each new
  one individually before assuming any of them represent real,
  unapplied content.

## A background CTS sweep launched before a mid-session rebuild uses a stale `libfeme_vulkan.so`

- A long-running `deqp-vk` process loads `libfeme_vulkan.so` once, at ICD
  load time, and keeps that in-memory copy for its entire lifetime --
  rebuilding the shared library on disk afterward (e.g. `ninja
  libfeme_vulkan.so` for a second fix landed later in the same session)
  does **not** affect an already-running process's loaded code, even
  though the file on disk is now newer. A background full-group sweep
  launched to "get a fresh baseline after this fix" is only valid for
  whatever fix(es) existed in the library *at the moment the sweep's
  `deqp-vk` process actually started* -- not whatever was most recently
  built by the time the sweep finishes.
- Concretely: a sweep launched right after fix A landed, left running
  into a second session where fix B then also lands and rebuilds the
  same `.so`, is now stale -- its eventual results will reflect fix A
  only, silently missing fix B's effect, with no error or warning of any
  kind (it just quietly under-reports how many cases now pass).
- Before trusting a long-running sweep's results, compare the `.so`'s
  mtime (`ls -la build/lib/libfeme_vulkan.so`) against the sweep
  process's own start time (`ps -o lstart= -p <pid>`). If the `.so` is
  newer than the process start, the in-flight sweep is running stale
  code -- kill it (a single `kill <pid>`, not `pkill`) and relaunch
  fresh rather than waiting for results that will not reflect the
  current source tree. Confirmed this session: `L444`'s own
  `opquantize`-fix-triggered re-sweep was still running into the next
  session when that next session's `opptraccesschain` fix rebuilt the
  same `.so` mid-sweep; caught before trusting the eventual (stale)
  numbers by this exact mtime-vs-start-time check.

## A lit test that `clang -c`'s a `feme-opt -S` lowered module needs its target datalayout/triple stripped first

- `feme-opt`'s lowering passes (`feme-cpu-linearize`/`feme-cpu-simdize`/
  `feme-cpu-lower-wave`/`feme-cpu-wrap-entry`) never rewrite a module's
  `target datalayout`/`target triple` -- whatever logical, DXIL/SPIR-V-
  style layout the input IR started with (carried over verbatim from
  FeMe's own import step, not any real target's) is still there in the
  `-S` output. The real AOT/JIT pipeline (`Target/CPU/Pipeline.cpp`,
  `CompiledStage.cpp`) always retargets a module to
  `getHostDataLayout()`'s real host layout immediately before codegen --
  but a lit test that invokes `clang -c` directly against raw `feme-opt
  -S` output, instead of going through that pipeline, skips this step
  entirely.
- On most hosts this mismatch is silently harmless (clang just emits an
  `-Woverride-module` warning and proceeds to compile against its own
  real host defaults anyway). On others it is not: confirmed on
  arm64-apple-macosx, where the logical layout's ELF-style `m:e` name
  mangling and `i8:8:32`/`i16:16:32` alignment overrides conflict with
  that target's real Mach-O `m:o` scheme and natural alignment closely
  enough that clang's backend fatal-errors ("Can't create a
  MachineFunction using a Module with a Target-incompatible DataLayout")
  instead of just warning. This is a real, host-dependent crash, not a
  flaky test -- it will reproduce deterministically on any host whose
  real datalayout differs from the logical one in the same specific ways.
- If a new lit test needs to `clang -c` a `feme-opt -S`-lowered module
  directly (so far only `linearize-defer-loop-body-mask-op-diamond.ll`),
  strip the `target datalayout`/`target triple` lines first and let
  clang fall back to its own true host defaults, e.g.: `grep -v -e
  '^target datalayout' -e '^target triple' %t/lowered.ll | clang -O0 -x
  ir - -c -o %t/lowered.o` (piped through `-x ir -`, not written to an
  intermediate file, to avoid needing a second `%t` path). This is
  exactly what the real pipeline's own retargeting step would have
  produced, and sufficient for any test that only checks a lowered
  function's runtime behavior, not its on-disk target metadata.

## A lit test that `clang`s a plain C harness file can't rely on the host's default SDK/sysroot headers

- `linearize-defer-loop-body-mask-op-diamond.ll` (see the previous lesson
  above for its first, unrelated macOS crash) has a second RUN line that
  compiles a hand-written C "harness" file (`split-file`'s `harness.c`)
  with a bare `clang -O0 %t/lowered.o %t/harness.c -o %t/run` -- no
  `-isysroot`, no `%clang` lit substitution, nothing SDK-aware.
- On Linux this is invisible: the freshly built, in-tree `clang` binary's
  own default header search paths happen to already include the system
  libc's headers. On macOS it is not: confirmed `fatal error: 'stdio.h'
  file not found` -- a freshly built, non-Xcode-wrapped `clang-24` does
  not auto-discover the active Xcode/Command Line Tools SDK's
  `usr/include` the way Apple's own shipped `/usr/bin/clang` driver does
  (that auto-detection is an Apple-clang-specific `xcrun`/`SDKROOT`
  behavior, not something upstream LLVM's driver replicates by default
  without an explicit `-isysroot`/`DEFAULT_SYSROOT` configuration).
- Any lit test that needs to compile-and-run a plain C/C++ harness file
  this way is exposed to the same failure on macOS, regardless of
  whether the harness file's own content has anything to do with FeMe.
  Since the Linux dev host can't reproduce or directly verify a
  macOS-specific sysroot fix, the robust fix is to make the harness file
  itself not depend on the host's SDK/system headers at all, rather than
  trying to patch in the right `-isysroot` from a host that doesn't have
  the problem:
  - Replace `<stdint.h>`'s `int32_t`/`int64_t`/`int8_t` with Clang's
    always-predefined `__INT32_TYPE__`/`__INT64_TYPE__`/`__INT8_TYPE__`
    builtin macros (defined on every target, no header needed).
  - Replace `<string.h>`'s `memset`/`memcpy` with equivalent hand-rolled
    loops -- at `-O0` these stay plain loops rather than being
    re-recognized as libcall idioms, so this doesn't introduce a new
    hidden libc dependency either.
  - Replace `<stdio.h>`'s `printf`/`fprintf` declarations with a local
    `extern int printf(const char *, ...);` prototype (the platform's C
    library still provides the actual symbol at link/run time; only the
    header-based declaration is avoided). Avoid `fprintf(stderr, ...)`
    specifically -- `stderr` itself is not a portable symbol to declare
    without its real header (e.g. Apple's libc only exports it as
    `__stderrp` under the `stderr` macro, so a bare `extern void
    *stderr;` would fail to link on macOS even though it compiles fine
    everywhere else). Route all diagnostic output through `printf`
    instead if the test doesn't actually need stdout/stderr separation.
- If a future lit test's harness genuinely cannot avoid a real SDK
  header (e.g. it needs a non-trivial libc/OS API with no builtin
  equivalent), prefer fixing this at the `feme/test/lit.cfg.py` level
  (a platform-aware substitution, e.g. adding `-isysroot
  $(xcrun --show-sdk-path)` only under `REQUIRES: system-darwin`) rather
  than patching each test's RUN line individually.

## A `run_vulkan_cts.py`/`deqp-vk` "before" baseline saved without checking its own `qpa` vendorID can be silently the wrong driver

- Per-session `VK_ICD_FILENAMES` must be exported fresh in *every* separate
  `bash` tool invocation (it does not persist across them) -- the mandatory
  per-session `vulkaninfo --summary | grep deviceName` check only proves
  the *current* shell has the right ICD selected, not that a `deqp-vk`
  sweep launched moments later in a *different* `bash` call (or via
  `run_vulkan_cts.py`, which spawns its own `deqp-vk` subprocesses) also
  had it set. A baseline CTS sweep captured this way, with the export
  silently missing from the actual sweep-launching command, runs against
  this container's system-default ICD (`lavapipe`/Mesa's `lvp_icd.json`)
  instead of `feme_vulkan` -- and produces a plausible-looking, fully
  self-consistent `report.txt` (deterministic Pass/Fail/NotSupported
  counts, no crashes) with **no indication anything is wrong**, since
  `lavapipe` is a real, working Vulkan driver in its own right. Found this
  the hard way (`L456`): three separate CTS "before" baselines captured
  earlier in this same session (`*denorm*`/`float_controls.*`/
  `glsl.builtin.precision.*`) each silently ran against `lavapipe`,
  producing a large, completely spurious 446-case "Pass -> NotSupported"
  diff against the real post-fix FeMe run that had nothing to do with the
  code change at all (the flagged cases were failing a `16BitStorage`
  feature check FeMe has hard-coded `VK_FALSE` since before this session
  even started).
- **The fix**: every saved CTS `qpa` file's own `#sessionInfo vendorID`
  line is a free, always-present, zero-effort way to confirm which driver
  actually produced it, after the fact -- `grep -m1 vendorID` any
  `output-dir/qpa/*.qpa` file and compare against FeMe's own hard-coded
  `FeMeVendorID = 0x10000` (`PhysicalDeviceInfo.cpp`) vs. Mesa's
  `0x10005` (the value both `lavapipe` and `llvmpipe`'s `vulkaninfo`
  itself report as `deviceName = llvmpipe (LLVM ..., 128 bits)`, i.e. the
  wrong-ICD give-away `vulkaninfo --summary` would have caught if run in
  the *exact* command that launched the sweep). Do this check on **every**
  CTS baseline/comparison report before trusting any diff against it, not
  only when a diff looks suspicious -- a baseline that happens to produce
  a diff of exactly zero against the wrong driver would otherwise look
  identically trustworthy to a correct one.
- When a "before" baseline turns out to be invalid this way, there is no
  shortcut: re-capture it from a genuinely pre-fix build (e.g. `git stash
  push -- <the fix's files>`, rebuild `libfeme_vulkan.so`, rerun, `git
  stash pop`, rebuild again) rather than trying to salvage or reinterpret
  the wrong-driver data.

## `FEME_DEBUG_DUMP_SPIRV_MLIR=1` could crash on modules that would otherwise compile fine (fixed upstream)

- This debug env var (`SPIRVImporter.cpp`) dumps the raw imported SPIR-V
  MLIR module by calling `Operation::print`, which forces a verification
  pass a normal, non-dumping compile never exercises. Confirmed in a prior
  session: using it against `Feature/WaveOps/WaveActiveAnyTrue.test`
  (whose only resource is an `RWBuffer<int>`, i.e. a SPIR-V image-buffer
  using `OpImageRead` under the hood, nothing visibly "image"-like at the
  HLSL source level) crashed with `mlir/lib/Dialect/SPIRV/IR/ImageOps.cpp:
  221: verifyImageOperands: Assertion '!spirv::bitEnumContainsAny(...)
  "unimplemented operands of Image Operands"' failed`, even though the
  module compiles and runs correctly through the normal, non-dumping
  path.
- **Root-caused and fixed** (upstream MLIR, outside FeMe): only reproduces
  via **`clang-dxc`**-compiled SPIR-V (plain `dxc` does not reproduce it
  for the same source) because `clang-dxc`'s codegen for an
  `RWBuffer<int>` read emits `OpImageRead ... SignExtend` (the signed
  scalar result requires sign-extension from the image's `R32i`/`R32ui`
  storage format), and upstream `verifyImageOperands` had a bare
  `assert(!bitEnumContainsAny(..., noSupportOperands))` that unconditionally
  treated `SignExtend`/`ZeroExtend` as "unimplemented," aborting the whole
  process on any legal module using them, instead of returning a
  diagnostic (or, better, actually validating and accepting them). Per the
  SPIR-V spec's own Image Operands operand-count table, `SignExtend`/
  `ZeroExtend` carry no accompanying `<id>` operand (pure result-conversion
  flags), so the fix implements real validation for them (including
  rejecting the spec-illegal combination of setting both bits
  simultaneously) rather than merely removing them from the assert list.
  Fixed in `mlir/lib/Dialect/SPIRV/IR/ImageOps.cpp`, with a new lit test
  (`mlir/test/Dialect/SPIRV/IR/image-ops.mlir`) covering accept/
  accept/reject for `SignExtend`/`ZeroExtend`/both. Since this bug lives
  entirely outside `feme/`, it was committed on its own, touching only
  non-FeMe files, per the standing "issue outside FeMe" process.
- The remaining `noSupportOperands` entries (`ConstOffset`, `Offset`,
  `ConstOffsets`, `MinLod`, `MakeTexelAvailable`, `MakeTexelVisible`) are
  still only partially implemented (still asserts, not a clean
  diagnostic) -- if a future session hits a *different*
  `FEME_DEBUG_DUMP_SPIRV_MLIR` crash on one of those operand kinds, apply
  the same pattern: identify the exact operand's SPIR-V-spec operand
  count/semantics, implement real validation, and replace the assert
  entry for just that operand (don't bulk-remove the whole list without
  individually confirming each one's operand-count/validation rules).
- **Workaround that worked**: use `spirv-dis` (a system-installed LunarG
  tool, `/usr/bin/spirv-dis`) directly on the compiled `.o`'s own SPIR-V
  binary instead (confirmed via `file`: these `.o`s are raw SPIR-V, not
  wrapped in a `DXContainer`, so `spirv-dis` reads them with zero
  preprocessing). This bypasses FeMe's own MLIR-based importer/dumper
  entirely and never hits whatever this crash's own root cause is.

- `Feature/ResourcesInStructs/res-of-matrix-in-struct.test` (a SIGABRT)

## `ninja clang` does not rebuild `llc` even when a shared static library changed

- `clang`/`clang-24` and `llc` both link `libLLVMSPIRVCodeGen.a` (and most
  other LLVM component libraries), but they are *separate* ninja targets.
  `ninja clang` relinks only `clang-24`/`clang`, not `llc`, even right
  after a source change rebuilds and relinks the shared static library
  both depend on. Running `ninja clang` alone after editing
  `llvm/lib/Target/SPIRV/*.cpp` leaves a stale `bin/llc` in place -- any
  earlier test/repro run through bare `llc` will keep reflecting
  whatever source state was in the tree the *last* time `llc` itself was
  explicitly rebuilt, independent of `clang`'s own freshness.
- This caused real confusion this session: a hand-written `.ll` lit test
  run through `llc` appeared to never reproduce a bug that a full
  `clang-dxc`-driven repro reliably reproduced, across many combinations
  of `-O0`/`-O3`/`-mtriple`/`-spirv-ext=...` flags -- the actual
  difference was never any of those flags, it was a stale, previously-
  fixed `llc` binary sitting untouched through several `git stash`/
  `ninja clang`/`git stash pop` cycles used for red/green sanity-checking
  the fix. Once `llc` was explicitly included in the `ninja` invocation
  (`ninja clang llc`), the standalone `.ll`-driven `llc` repro matched
  the `clang-dxc` repro exactly, both for the bug and the fix.
- **Takeaway**: whenever doing a source-reverted/applied red/green check
  across more than one LLVM driver binary (`clang`, `llc`, `opt`, etc.),
  explicitly name every binary you intend to test against in the same
  `ninja` invocation (e.g. `ninja clang llc opt`) rather than rebuilding
  one and assuming the others -- which link the same just-changed
  library -- are equally current.

## `SIMDize.cpp`'s per-lane GEP decomposition is invalid for non-byte-addressable vector elements

- `FunctionWidener`'s divergent-vector-load/store widening (`widenGroupSharedLoad`,
  `widenMaskedLoad`, `widenMaskedStore`'s groupshared-scatter path) decomposes a
  vector-typed load/store into one `getelementptr <VecTy>, WidePtr, {0, Idx}` +
  `masked.gather`/`masked.scatter` pair *per lane*. This is only valid when the
  vector's element type is byte-addressable (`DL.typeSizeEqualsStoreSize(ElemTy)`
  true, e.g. `float4`'s `float` lanes). For a `bool2`/`bool3`/`bool4`
  (`<N x i1>`) row, LLVM bit-packs all lanes into the same byte(s) with no
  well-defined per-lane byte offset, so this GEP shape is architecturally
  invalid IR -- not merely a slow path or an unsupported optimization, a real
  violation that LLVM's own `gep_type_iterator::getSequentialElementStride`
  asserts on ("Not byte-addressable").
- This is now guarded (reports `Ctx.emitError`/`HadError=true` instead of
  crashing) at all three `SIMDize.cpp` call sites, plus matching
  defense-in-depth bailouts in three LLVM-core helpers
  (`GEPOperator::accumulateConstantOffset`/`collectOffset` in `Operator.cpp`,
  `TargetTransformInfoImplBase::getGEPCost`, and `InstCombinerImpl::
  visitGetElementPtrInst`'s "strip leading zero indices" canonicalization) --
  see roadmap `L459`.
- **Why this crash kept moving between LLVM passes while under investigation**:
  once the illegal GEP exists in FeMe's own pre-optimization IR (confirmed via
  `FEME_DUMP_IR_PREOPT=1`, not introduced by any LLVM pass), *any* LLVM pass
  that queries its byte stride will hit the same assertion, but at whichever
  of several possible call sites that specific pass's own code path happens to
  reach first (`EarlyCSE` via `accumulateConstantOffset`, `FunctionSpecializer`/
  `IPSCCP` via `getGEPCost`, various `InstCombine` optimizations via
  `emitGEPOffset`). Patching one call site just moves the crash to the next
  one reachable from a different optimization-pipeline ordering -- this made
  the bug initially look like unbounded upstream-LLVM whack-a-mole until
  `FEME_DUMP_IR_PREOPT` proved the GEP itself, not any one caller, was the
  real problem.
- **Not yet fixed**: a real fix needs a genuine bit-packed gather-then-shift-
  extract redesign for sub-byte vector rows (load the whole packed
  representation per lane, then extract each bit), mirroring the existing
  `buildBoolVectorGEP`/`BoolVectorLaneLoadPattern` precedent in
  `SPIRVToLLVMPatterns.cpp` (which already correctly avoids this exact trap by
  loading the whole vector and using `extractelement`, never indexing a lane
  via `getelementptr`). Same complexity class as the still-open `L419(ae)`
  tessellation issue -- out of scope for a quick patch.

## The `requiredsubgroupsize128` "stall" is a real but finite LLVM backend compile-time scaling issue, not a hang

- Follow-up to the previous note above (same anomaly, now isolated). Narrowed
  the repro from the full 6117-case `ballot_broadcast` sweep down to a single
  case (`subgroupbroadcast_int_requiredsubgroupsize128` alone): it is **not**
  an infinite hang, it genuinely takes ~79 seconds to compile and pass.
- 5 independent `gdb -batch -ex attach -ex bt -ex detach` samples taken at
  20s/30s/40s/50s/60s into the run all land inside plain upstream LLVM CPU
  backend codegen (`MachineScheduler`/`ScheduleDAGInstrs::buildSchedGraph`,
  `RegAllocGreedy`/`InlineSpiller`, `SelectionDAGISel`'s instruction
  scheduler, `BasicAAResults::aliasCheck`) -- never any FeMe code. This is a
  real algorithmic-complexity characteristic of these passes (several are at
  least `O(n^2)` in basic-block/function size) applied to an unusually large
  function: `requiredSubgroupSize=128` forces `SIMDize.cpp` to widen to a
  128-lane vector width, producing a correspondingly huge compiled function.
- **Scope is small**: of `ballot_broadcast`'s 18 total
  `*_int_requiredsubgroupsize128`/`*_uint_requiredsubgroupsize128` cases
  (the only scalar 32-bit types that pass this device's subgroup-format
  check at that width), only 6 actually reach codegen (the rest are
  `NotSupported` for an unrelated reason, e.g. `VK_EXT_shader_subgroup_ballot`
  not being advertised) -- those 6 together take 2m41s, not indefinitely.
  `vec8_int`/`vec8_uint` variants at the same subgroup size are
  `NotSupported` before ever reaching codegen, so they don't make this worse.
- **Not a bug, not fixed this session**: a real fix would mean changing the
  CPU backend's codegen strategy for extreme-width (128-lane) vectorized
  functions (e.g. splitting into narrower chunks, or a different scheduling
  heuristic) -- a genuine design-level undertaking, out of scope for a
  quick patch. Documenting so a future full `subgroups.*` sweep isn't
  mistaken for hanging again: if progress is visibly continuing (just slow)
  on a `requiredsubgroupsize128` case, let it run; it will finish.

## A `--heap` YAML entry for a Typed buffer (`RWBuffer<T>`) needs `kind:`/`format:`, not just `size:`

- Discovered while hand-writing a heap YAML for a `feme-run` Typed-buffer
  atomic (`RWBuffer<uint>`) repro/lit test. A heap entry that only specifies
  `size:` (the minimal shape that works for a `RWStructuredBuffer`/raw
  buffer) silently produces an all-zero/no-op result for a Typed buffer --
  no error, no crash. The runtime's `femeRTAtomicResourceAddress`
  (`FeMeRuntimeCPU.c`) and friends compute `ElemSize` from
  `femeRTImageFormatElementSize(Desc.Format)`; if `Desc.Format` was never
  populated (no `format:` key) it comes back as an unrecognized format and
  the address helper returns `NULL`, which the surrounding code then quietly
  treats as a no-op rather than erroring.
- **Fix/workaround**: always add both `kind: typed-buffer` and a
  `format: <format>` (e.g. `r32_uint`) to any heap YAML entry for a Typed
  buffer -- see `typed-buffer.hlsl`'s existing lit test for the convention,
  and `resource-atomic.hlsl`'s `typed-heap.yaml` split-file part for another
  worked example (added this session, alongside the DXIL resource-atomic
  raising/lowering fix that made Typed-buffer atomics reachable at all).
- This is not a new bug -- it is a pre-existing, easy-to-miss heap-YAML
  schema requirement that only bites when hand-writing a Typed-buffer heap
  entry from scratch rather than copying an existing one.

## A loop header phi's value, read from a block it dominates after the loop exits, is one masked-SIMD-group iteration stale

- A `Header`-resident loop phi's value, read directly (via plain SSA
  dominance, not through a fresh per-exit-edge phi) from any block
  `Header` dominates after the loop's masked latch has stopped looping,
  reflects that phi's value *as of entering* the iteration during which
  the group's masked loop finally stopped -- not any additional
  freeze/update `Latch` computes *during* that same, final iteration.
  For a single-lane (or always-uniform) loop this distinction is
  invisible (there is no "other work Latch still does this iteration"
  to miss), but for a masked SIMD loop where different lanes can diverge
  on different iterations, a lane whose masked group happens to share a
  late, common final active iteration will read the *previous*
  iteration's frozen value instead of the correct, freshly-recomputed
  one from the final iteration itself.
- `freezeLoopCarriedValues`'s own `FeedsUniformBranch` shadow-phi
  mechanism (`Linearize.cpp`, `L464`/`L467`) hit exactly this shape:
  outside-the-loop uses were redirected straight to the shadow's raw
  `Header` phi (valid SSA, since `Header` dominates every reachable exit
  block), which is one iteration stale for the reason above. The fix
  (`L467`) defers that redirection until after the shadow phi's own
  self-reprocessing (the same `Header->phis()` scan revisiting its own
  newly-appended node) has finished computing its fully-resolved,
  this-iteration value, then re-resolves each use to that value instead
  -- substituted directly when the use is itself a phi already resident
  in the loop's exit block (a generic new merge phi there would not
  dominate `Latch`, an illegal operand for that specific incoming edge),
  or via a dedicated new exit-block merge phi otherwise.
- **Takeaway for any future "value read after a masked loop looks subtly
  wrong only for some lanes" bug**: check whether the value in question
  is read via plain dominance from a `Header`-resident phi (as opposed
  to a fresh, per-edge-correct exit merge) before assuming the bug is
  elsewhere -- this exact "stale by one masked-group iteration" shape is
  easy to miss since it only differs from correct behavior on a late,
  shared final iteration, not on every iteration.

## A non-phi `Header`-resident value read outside the loop needs freezing too -- and with the *entering* mask, not the exiting one

- `freezeLoopCarriedValues` only ever scanned `Header`'s own *phis* for
  values needing a frozen-on-exit shadow (`L464`-`L467`). A value
  computed fresh every iteration from loop-carried phis but that is
  *not itself a phi* (e.g. `X*X + Y*Y`, derived from loop-carried `X`,
  `Y`) can still be read directly outside the loop with no phi of its
  own, whenever it happens to dominate the exit block -- most commonly
  via CSE folding an identical post-loop re-computation into the same
  in-loop SSA value. This went completely unfrozen before `L468`: every
  lane in a masked group except the one with the group's own
  longest-running iteration count ended up reading that lane's own
  later, further-recomputed value instead of its own value as of its
  individual exit.
- **The mask matters, and gets it backwards if copied from the ordinary
  phi case.** An ordinary loop-carried phi's update is gated by
  continuing past the branch decision, so freezing it with the
  *exiting* mask (`BodyMask`, computed *after* the branch) is correct --
  it keeps the pre-check value for a lane that exits this round. But a
  value that *feeds* the branch condition (like `X*X+Y*Y` feeding
  `Diverged`) is computed *before* the exiting mask is even decided, so
  the round's own freshly-computed value is exactly what a lane exiting
  *this* round needs kept. Freezing it with the exiting mask discards
  that value and keeps the group's one longest-running lane's own
  ever-growing post-divergence value for everyone else instead --
  confirmed empirically in `L468`'s first fix attempt: 87.6% of pixels
  wrong, up from the original 1.25%. The correct mask is the *entering*
  one (`MaskPhis.front()`/`Masks.Live`, i.e. "was this lane still
  looping as of the start of this round").
- **`check-feme`'s own lit/unit coverage did not catch the
  wrong-mask regression.** None of its ~3820 tests exercise Clang's real
  `Basic/Mandelbrot.test` shader, so the severely-broken first attempt
  passed `check-feme` cleanly while catastrophically breaking real-world
  rendering. For any fix in this file (or anywhere masking/freezing
  logic is touched), a direct pixel-diff/`imgdiff` check against a real
  compiled shader artifact remains the only way to catch this class of
  regression -- `check-feme` alone is not sufficient evidence.

## Freeing the host for a build while a background CTS sweep runs: `SIGSTOP`/`SIGCONT` the real `deqp-vk` workers, don't kill the sweep

- The "no `ninja`/build work while a background `ENV4`-style CTS sweep is
  active" rule's real purpose is avoiding CPU contention (confirmed by
  a prior session's real SIGSEGV-under-17-worker-overcommit incident),
  not mere process coexistence. A multi-hour sweep does not need to be
  killed (losing all progress) or waited out in full before any
  compiler-fix work can start in the same session.
- **`kill -STOP <pid>` on each real `deqp-vk` worker process** pauses it
  with zero further CPU usage while fully preserving its in-memory
  state (confirmed via `ps -o stat` showing `T`), reversibly resumable
  later via `kill -CONT <pid>` with no lost progress -- the driver
  script (`run_vulkan_cts.py`) and its shell wrapper are left running
  and simply block harmlessly on `waitpid` for the stopped children.
- **Identify the real worker PIDs precisely**, not just anything
  mentioning `deqp-vk`: `ps -eo pid,cmd | grep '/vulkan/deqp-vk '` (note
  the trailing space after the binary name) matches only the actual
  `deqp-vk` binary invocations, excluding the Python driver and its
  `xvfb-run`/shell wrapper, both of which merely pass `--deqp-vk <path>`
  as one of their own arguments and must **not** be stopped (stopping
  the driver itself would desynchronize it from its own child-process
  bookkeeping, unlike pausing a worker it is already blocked on).
- This session's `bash` tool only accepts one literal numeric PID per
  `kill` invocation -- no `$()`-command-substitution loops, no bulk
  `-9`/`-STOP` across a shell-expanded PID list. Each worker must be
  stopped (and later resumed) with its own separate `kill -STOP
  <PID>`/`kill -CONT <PID>` call.
- Always resume every paused worker (`kill -CONT`) before ending a
  session that used this technique, and re-verify via `ps -eo
  pid,stat,cmd | grep '/vulkan/deqp-vk '` that the sweep is actually
  progressing again afterward -- don't just issue the `kill -CONT` calls
  and assume they worked.

## `clang-format -i` on a whole FeMe/MLIR source file can reformat thousands of unrelated lines -- always diff-scope it

- Several existing `feme/`/`mlir/` source files (e.g.
  `SPIRVToLLVMPatterns.cpp`, `SPIRVToLLVMTest.cpp`) are not fully

## When a Vulkan-pipeline bug's error message doesn't name a shader stage, dump IR for every stage before committing to one hypothesis

- A multi-shader-stage Amber/CTS test (e.g. a graphics pipeline with
  separate vertex/fragment shaders) throws one shared MLIR/LLVM
  verifier error regardless of which stage's conversion actually
  produced it. An error like `'llvm.load' op operand #0 must be LLVM
  pointer type, but got 'i32'` carries no stage information at all.

  repro, a temporary pass-manager split for extra dump points) into one
  stage's plausible-looking bug shape, only to find the *other* stage was
  the actual culprit, is a real failure mode this project has now hit
  once. The two candidate shapes (a fragment shader's `OpSelect`-over-
  null and a vertex shader's trivial `OpCopyMemory` passthrough) looked
  equally plausible from the error text alone.
- **Before spending more than ~15-20 minutes on a single-stage
  hypothesis**: dump the raw `spirv.module` for *every* shader stage in
  the failing pipeline (`FEME_DUMP_IR_PRESPIRV=1` in
  `SPIRVToLLVMDialectTranslator.cpp`, the earliest dump point, predating
  even `FEME_DUMP_IR_PRENORM`) against the real failing `deqp-vk`

  stage's *own* conversion call throws before digging into either one's
  internals.
- Once the right stage is identified, extract just that stage's
  `spirv.module` text into a standalone `.mlir` file and iterate via
  `feme-opt --pass-pipeline="builtin.module(feme-convert-spirv-to-llvm)"`
  directly -- far faster than rebuilding/rerunning the whole ICD per

## `git clang-format`/`git checkout --` near-miss: never `checkout --` a file to "clean up" a failed in-place reformat

- This session nearly lost a large (~450-line), entirely uncommitted
  bugfix by mishandling the formatting step this file's own earlier

  HEAD -- <file>` (no `--diff`) refused with "would be modified but have

  immediately preceding command touched. Never use either as a "retry"

  non-conformant file (confirmed working this session):
  `clang-format-diff -p1 -i < <(git diff -U0 -- <file>)` -- reformats
  only the changed lines directly in the working tree (no commit/stash
  prerequisite, no risk of a destructive retry), then rebuild and rerun
  tests to confirm the reformat didn't change semantics.

## `FEME_VULKAN_LOG_CREATION_ERRORS=1` surfaces the real `vkCreateGraphicsPipelines`/`vkCreatePipelineLayout` error string

- By default, a Vulkan pipeline/layout-creation failure observed via
  `deqp-vk` (e.g. `vkCreateGraphicsPipelines Fail`) swallows FeMe's own
  real error string, leaving only the bare Vulkan result code in the
  CTS log -- not enough to diagnose anything beyond "something about
  this pipeline is rejected."
- Set `FEME_VULKAN_LOG_CREATION_ERRORS=1` (checked in
  `feme/lib/Vulkan/Diagnostics.cpp`) to have FeMe print its own detailed
  error string (e.g. `no hull entry point named 'main.patchconstant'`)
  to stderr before returning the failure code. Combine directly with a
  standalone `deqp-vk --deqp-case=<one case>` invocation for fast
  iteration -- this is usually the very next thing to reach for whenever
  a pipeline-creation failure has no other diagnostic attached, before
  reaching for `gdb` or any `FEME_DUMP_IR_*` dump.
- A "no diagnostic at all" cluster from any log-clustering script that
  only matches lines starting `error:` can be a false negative, not a
  real absence of diagnostic text: `vkCreateGraphicsPipelines`'s own
  summary line (e.g. `vkCreateGraphicsPipelines: feme-cpu-linearize:
  'main' produced a module that fails IR verification ...`) and LLVM's
  own verifier output (e.g. `Instruction does not dominate all uses!`)
  don't start with `error:`, so a regex keyed on that prefix alone will
  silently fold real, logged-elsewhere compiler bugs into the "silent
  rendering-correctness Fail" bucket. **Always re-run every "no
  diagnostic" case individually with `FEME_VULKAN_LOG_CREATION_ERRORS=1`
  before concluding it's a pure rendering bug** -- this surfaced a
  9-case genuine compiler bug (`Linearize.cpp`'s `ShadowExitFixups`
  dominance violation) that a prior session's `^error:`-only clustering
  had mis-bucketed as "no diagnostic" alongside true silent-rendering
  cases.

## MLIR discardable attributes silently vanish through a custom op printer that skips the attribute dictionary; `CloneFunctionInto`/`copyAttributesFrom` silently inherit them onto unrelated clones

- Not every MLIR op's custom assembly format calls
  `printOptionalAttrDict`/`parseOptionalAttrDict`. `spirv::EntryPointOp`'s
  does not (confirmed by reading `SPIRVOps.cpp`'s `EntryPointOp::print`/
  `::parse`) -- so any discardable attribute attached to an
  `EntryPointOp` is genuinely present in-memory (visible via
  `-mlir-print-op-generic` *within the same process*) but is **silently
  and irrecoverably dropped the instant the module is printed to text
  and reparsed**, e.g. piping output between two separate tool
  invocations (`mlir-translate | feme-opt`). Debug prints added
  immediately after the attribute's creation will show it correctly even
  while this bug is present, because by that point the text has not yet
  round-tripped -- this makes the bug easy to "fix" wrongly and declare
  done. Before attaching a discardable attribute to any op to make it
  survive a pass pipeline or tool boundary, confirm that op's custom
  printer (if it has one) actually emits an attribute dictionary; prefer
  attaching it to a plain function/op with the default/generic printer
  (e.g. `spirv.func`, which was confirmed to round-trip discardable
  attributes correctly) if the op you'd naturally reach for doesn't.
- `llvm::CloneFunctionInto` and `Function::copyAttributesFrom` both copy
  **every** function attribute from source to destination, including any
  FeMe-internal bookkeeping attribute that has nothing to do with the
  clone's own identity (e.g. `feme.entry.name`, which must not leak from
  a tessellation control entry point onto its synthetic
  `<entry>.patchconstant` sibling clone). When introducing a new
  function-level attribute meant to be per-function-identity (not
  inherited along with a function's body), audit every
  `CloneFunctionInto`/`copyAttributesFrom` call site in `feme/` that
  clones a function the attribute might land on, and strip it
  immediately after the copy if the clone needs its own distinct value
  (or none at all) -- this is easy to miss since the resulting failure
  surfaces only through whichever downstream consumer reads that
  attribute, with no connection in the error message back to the
  attribute-copying call site itself.

## Two MLIR conversion patterns at the same `PatternBenefit` do not reliably try in registration order; give each pattern its own precise structural guard instead of relying on try-order

- `SPIRVToLLVMPatterns.cpp` registers `BlockWholeCopyMemoryPattern` and
  `StageIOCopyMemoryPattern` for `spirv.CopyMemory` at identical
  `FeMeBenefit`, with `BlockWholeCopyMemoryPattern` listed *first* in the
  `Patterns.add<...>()` call. Reading `RewritePatternSet::add` (a
  guaranteed left-to-right comma-fold), `FrozenRewritePatternSet`'s
  per-op bucket construction (iterates in insertion order), and
  `PatternApplicator::applyCostModel`'s `llvm::stable_sort` (stable,
  preserves insertion-order ties) all suggested `BlockWholeCopyMemoryPattern`
  should be tried first. Empirically (`feme-opt --debug`), it was not:
  `StageIOCopyMemoryPattern` was tried and incorrectly succeeded first
  for a shape (a resource-handle source) it was never meant to handle,
  because its own guard was purely structural ("source is not yet a
  real `!llvm.ptr`") and happened to also match a handle type. This
  reversal was investigated but not conclusively explained.
- **Lesson**: never rely on registration order or a shared
  `PatternBenefit` to keep two same-op patterns from colliding on a
  shape neither author anticipated the other covering. Give each
  pattern's `matchAndRewrite` guard the most precise structural check
  available for the shape it actually targets (e.g. explicitly
  exclude `LLVMTargetExtType` sources rather than only checking "not a
  pointer yet") so it declines correctly regardless of try-order. If a
  future session hits an unexplained "pattern X fired when I expected
  pattern Y" bug on an op with multiple registered conversion patterns,
  do not assume registration order is dispositive -- trace the real
  order with `--debug` first, then fix the guard, not the order.

## `checkGEPType`'s assertion is not exclusive to literal `GetElementPtrInst`s; and construction-side/access-side struct-type resolution must independently peel the exact same way

- `CanonicalizeStage.cpp`'s `variable_init.output.struct` crash hit
  LLVM's `"Invalid GetElementPtrInst indices for type!"` assertion with
  a `gdb` backtrace whose crashing frame (`canonicalizeSPIRVStage`) has
  no literal `GetElementPtrInst` calls of its own nearby -- initially
  looking like a misleading/stale backtrace. It was not:
  `ExtractValueInst`/`InsertValueInst` share the exact same underlying
  struct-member-index-range-checking code path (`llvm::checkGEPType`)
  as literal GEPs, so an out-of-bounds `CreateExtractValue`/
  `CreateInsertValue` on a struct produces the identical assertion
  text. **Lesson**: when this assertion fires from a frame with no
  obvious GEP, check for `ExtractValueInst`/`InsertValueInst` calls in
  that frame before assuming the backtrace is wrong or incomplete.
- Root cause of that crash was a now-recurring pattern in this file:
  two independent code paths (construction-side `addElements`, via
  `peelSingleMemberStruct`+`isGenuineMultiMemberNestedStruct`, versus
  access-side `getEffectiveStageIOValueType`/`resolveStageIOAccess`)
  must agree on a stage-IO global's "effective" (peeled) type for every
  shape, not just the shapes each side's author happened to think of
  first. The construction side already handled "single-member wrapper
  around a genuine multi-member nested struct" (an
  `MemberMD`-independent shape); the access side only peeled when
  `feme.spirv.MemberDecorations` metadata was present (a different,
  `Block`-decoration-driven case) -- a silent, easy-to-miss asymmetry
  that produced a crash only when a specific combination of shape
  (single-member wrapper, no `MemberMD`) and mechanism
  (`HasRealInitializer`'s synthesized whole-aggregate store) exercised
  the gap. **Lesson**: whenever adding or auditing a peel/shape-check
  in one of this file's construction-side or access-side helpers,
  search for the other side's equivalent helper and verify both use
  the *same* predicate/peel for the *same* set of shapes -- do not
  assume a new shape handled on one side is automatically handled on
  the other. A fix in one helper alone can also *move* the crash to a
  new location downstream (e.g. SIMDize's masked-store broadcast logic
  mishandling a still-wrong-shaped value) rather than resolve it --
  this is a signal the real source of the mismatch is further
  downstream (here, the `HasRealInitializer` synthesis code's own
  value construction) than the first helper touched, not a sign the
  first fix was wrong.

## `Linearize.cpp`'s fixed-point folds must guard against *earlier* applications in the same loop exposing a new alias, not just their own immediate-successor snapshot

- `foldRedundantFlowBlocksInCycle` applies `foldRedundantFlowBlock`
  repeatedly to a fixed point within one cycle. Each application's own
  checks (escaping-use validation, an immediate-successor
  `Targets[0]==Targets[1]` identity check) only reason about the CFG as
  it stands at the moment that specific application runs. They do not,
  and structurally cannot, know whether an *earlier* application within
  the same fixed-point loop already retargeted a downstream relay such
  that this application's own two, still textually-distinct `Targets`
  now reconverge at the exact same merge-phi slot before reaching any
  other merge point. When that happens, the forwarding loop's one
  `MergePN->setIncomingValue(Idx, Forwarded)` write per predecessor runs
  twice into the same slot, and the second write silently clobbers the
  first -- discarding one of two genuinely-different values with no
  diagnostic, surfacing much later as an "Instruction does not dominate
  all uses!" verifier failure (a crash, not a graceful decline).
- **Lesson**: a fold that is proven locally safe by checking "my own
  two targets differ" is *not* automatically safe when run to a fixed
  point alongside other folds in the same pass -- a fold run earlier in
  the same loop can make a later fold's own two "distinct" targets
  alias on a shared downstream merge slot. When writing or auditing a
  fold-to-fixed-point loop in this file, check not just "are my
  immediate successors distinct" but "have my successors' *eventual*
  merge destinations already been made to coincide by an earlier
  iteration" before forwarding a value into a shared phi slot -- bail
  out (leave the block standing) rather than guess which of two
  conflicting forwarded values to keep.
- **Diagnostic technique** (reusable for any future `Linearize.cpp`
  miscompile): `FEME_DUMP_IR_PRELINEARIZE=1 ./deqp-vk
  --deqp-case=... --deqp-log-images=disable` dumps every function's
  pre-linearize IR; extract the one crashing function's own module
  block into a standalone `.ll` (watch for trailing non-IR verifier
  text with no clear delimiter -- find the last real `!<N> = !{...}`
  metadata line by hand) and run it through `feme-opt --llvm
  -passes=feme-cpu-linearize,verify -S` for a fast, full-CTS-independent
  repro loop. `FEME_OPT_DUMP_INVALID=1` dumps the actual broken module
  even when verification fails and no `-o` file is written -- essential
  for inspecting what the (incorrect) transform actually produced.
  **Gotcha** (roadmap `L486`): including `,verify` as an explicit pass
  in `-passes=...` makes `VerifierPass::run` call `report_fatal_error`
  directly on failure -- a hard `LLVM ERROR: Broken module found` abort
  that bypasses `feme-opt.cpp`'s own post-`MPM.run()` `verifyModule`
  check entirely, so `FEME_OPT_DUMP_INVALID`'s dump path (which lives in
  that later check) never runs in that case. To get the dump of a
  broken module, omit `,verify` from `-passes=...` and let `feme-opt`'s
  own check catch it instead; keep `,verify` only when a clean,
  immediate pass/fail signal (exit code, stderr diagnostic) is all
  that's needed and the dump isn't.
  `FEME_DEBUG_PEEL_TRACE`/`FEME_DEBUG_FLATTEN_TRACE`/
  `FEME_DEBUG_LINEARIZE_TRACE` are each gated to one specific
  fold/pass; the *absence* of expected trace output (zero hits) is
  itself a reliable signal that pass never touched the IR in question,
  and can disprove an otherwise-plausible theory about which fold is at
  fault before any code is changed.

## A multi-entry-point-same-Name SPIR-V bug needs raw `spirv-as`-assembled test fixtures, not MLIR `spirv`-dialect text, and must be chased by (name, stage) not just by name

- **Context**: `dEQP-VK.spirv_assembly.instruction.graphics.module.
  same_module*` (`vktSpvAsmGraphicsShaderTestUtil.cpp`'s
  `createCombinedModule`) builds a single SPIR-V binary whose
  Vertex/Geometry/TessControl/TessEval/Fragment `OpEntryPoint`s all
  legally share one literal Name, "main" -- SPIR-V allows this as long
  as each is a different `OpEntryPoint` Execution Model. Deserialization
  keeps only the *first* such entry on the bare LLVM symbol and
  disambiguates every later one of a different stage onto a distinct,
  suffixed symbol (e.g. `main`, `main_5`, `main_8`...), while still
  recording the true, pre-disambiguation Name as each one's own
  `feme.entry.name` attribute (see `getEntryPointName`'s own comment).
- **Bug pattern this shape exposes, twice found this way**: any code
  that resolves "the function for entry point X" by a *bare LLVM
  symbol* lookup alone (`Module::getFunction(Name)`) rather than by
  `(Name, Stage)` together (`feme::findFunctionByEntryPointName`)
  silently resolves to the *wrong* stage's entry whenever more than one
  stage shares a Name -- it always finds whichever entry happens to
  still hold the bare, undisambiguated symbol, not necessarily the one
  being asked about. Grep for any new/existing `getFunction(` call near
  shader-stage-specific logic and prefer `findFunctionByEntryPointName`
  on principle, even if no known case currently shares a Name.
- **Test-fixture technique**: the existing `assembleSPIRV` test helper
  (MLIR `spirv` dialect textual parse → serialize) **cannot** express
  this shape at all -- MLIR enforces unique symbols per `spirv.module`,
  and `spirv.EntryPoint "<Model>" @symbol` serializes that symbol
  directly as the `OpEntryPoint` Name, so no MLIR `spirv.module` text
  can ever produce two `OpEntryPoint`s of different stages sharing one
  literal Name. Use raw `spirv-as --target-env spv1.3 -o out.spv
  in.spvasm` instead, hand-writing distinct SPIR-V IDs per stage (even
  though every stage's `OpEntryPoint` Name is the same "main" string),
  `spirv-val out.spv` to confirm validity, then dump the binary's words
  as a `constexpr uint32_t` C array (`struct.unpack('<%dI' %
  (len(data)//4), data)` in Python) for embedding directly in a test
  file via a `createModuleFromWords(ArrayRef<uint32_t>)` fixture helper
  that bypasses `assembleSPIRV`'s MLIR round trip. Keep every stage's
  shader interface self-contained (no real vertex-attribute `Input`s
  needing a matching `VkPipelineVertexInputState`; no varying a later
  stage doesn't also independently reproduce) so the fixture's only
  real dependency is on the multi-entry-point shape itself, not on
  unrelated pipeline wiring the test doesn't care about.
- **IR-inspection pipeline for confirming a SPIR-V import's
  disambiguation/attribute shape** (useful before writing a repro, to
  confirm symbol names/attributes without guessing): `feme-translate
  --import-spirv in.spv -o out.mlir` (spirv dialect text, inspect with
  `grep -n "spirv.func @\|spirv.EntryPoint"`), then `feme-opt
  out.mlir --feme-convert-spirv-to-llvm -o out_llvm.mlir` (llvm dialect
  text). Note: `feme-translate`'s own MLIR parser does **not** register
  the `llvm` dialect, so re-parsing `out_llvm.mlir` with any of
  `feme-translate`'s `--spirv-to-llvmir`/`--mlir-to-llvmir`/
  `--llvmdialect-to-llvmir` flags fails or silently produces an empty
  module -- there is currently no supported way to go from this
  intermediate llvm-dialect *text* file to real LLVM IR text via
  `feme-translate` alone; stop at the `spirv.func`/`spirv.EntryPoint`
  inspection step (sufficient to confirm symbol disambiguation and
  stage attributes) rather than chasing this further.
- **This fork's LLVM IR splits `BranchInst` into two distinct
  classes.** `llvm/include/llvm/IR/Instructions.h` has separate
  `UncondBrInst` (`Instruction::UncondBr`, one successor, no
  `isConditional()`) and `CondBrInst` (`Instruction::CondBr`) opcodes
  where upstream LLVM has a single `BranchInst` with
  `isConditional()`/`getNumSuccessors()`. Code written against upstream
  LLVM's own `BranchInst` API (e.g. `dyn_cast<BranchInst>(Term)` then
  `isConditional()`) will not compile/match here -- `dyn_cast` the
  specific class you actually expect (`UncondBrInst` for an
  unconditional terminator) instead. Any new pass code walking
  terminators needs to account for this split from the start; grep
  existing nearby code (e.g. `CanonicalizeStage.cpp`'s own
  `UncondBrInst::Create` call sites) for the established pattern before
  writing new terminator-matching logic.
- **A tessellation-control patch-constant phase is one non-batched,
  lane-0-only invocation per patch, not per control point**
  (`PatchConstantWrapper.cpp`'s own file comment). Before attributing
  *any* post-barrier work to the patch-constant phase during a
  `splitTessellationControlEntry`-style investigation, check what the
  value ultimately gets stored to: a write indexed by
  `gl_InvocationID`/an per-control-point `Output`-direction stage-IO
  global (check `!spirv.Decorations`/`!feme.spirv.MemberDecorations`
  for the absence of a `Patch` decoration) cannot be correctly
  represented there, no matter how the barrier call sites themselves
  are unified -- only genuinely per-patch/uniform (`PatchOutput`)
  writes are safe to move into that phase. This was the real blocker
  behind `ENV5(c)(7)(a)`'s `barrier.{in_if,in_switch}` re-triage
  (`VulkanCTSReport.md`'s `L487`), not the barrier-call-site-counting
  logic itself.
- **A hand-written `LinearizeTest.cpp`-style unit-test repro can give a
  false "already works"/"already fails differently" result** even when
  it matches a real bug's reported *shape* exactly, because the
  `LinearizePass().run(M, MAM)` test harness runs only that one pass --
  skipping `SPIRVResourceLoweringPass`/`SPIRVPushConstantLoweringPass`/
  `LoopSimplifyPass` (and other `Normalize`-group passes), all of which
  `feme::cpu`'s real pipeline (`Pipeline.cpp`) always runs immediately
  before `LinearizePass` on real IR. A resource/image call a hand-written
  repro writes directly (e.g. `feme.stage.subpass.load.*`, a raw
  `llvm.spv.resource.*` intrinsic) is not yet in the same lowered,
  mask-carrying form the real pipeline hands `LinearizePass`, so
  mask-affecting-operation detection (`cycleHasMaskOps`) and other
  shape checks can silently see a different (often "already fine")
  module than the real one. Whenever a unit-test result disagrees with
  a real `deqp-vk` run of the same bug, re-extract the *exact* real
  input via `FEME_DUMP_IR_PRELINEARIZE=1` (dumps immediately before
  `LinearizePass` itself runs, i.e. after every prerequisite pass) and
  feed that verbatim into the harness, rather than trusting a
  hand-simplified repro. Found debugging `ENV6(a)`'s `api.copy_and_blit`
  cluster (`VulkanCTSReport.md`'s `L489`).

## Fast-bisecting whether a crash is a genuine new regression: swap files in-place, don't build a second tree

- A `git worktree` for a second full LLVM build is extremely slow (this
  checkout has ~189k files) -- avoid it for a quick "did my change cause
  this, or did it already exist" bisection question.
- Instead, in the *same* working tree/build directory: `git checkout
  <prior-commit> -- <the specific files your change touched>`, rebuild
  only the affected target (e.g. `ninja feme_vulkan`), reproduce, then
  `git checkout HEAD -- <same files>` and rebuild again to restore. This
  reuses ccache for every untouched translation unit and the full
  dependency graph, so each half of the bisection is as fast as an
  ordinary incremental rebuild. Found while root-causing `ENV6(b)(1)`'s
  `depth_stencil_mapping_to_no_index` `SelectionDAGBuilder` crash
  (`VulkanCTSReport.md`'s `L504`).
- Whichever state you leave the tree in afterward matters: finish by
  restoring to `HEAD` (or whatever the intended next edit builds on)
  before resuming real work, and rebuild once more to confirm the tree
  and the built `.so`/binaries actually agree before trusting any
  further test run.

## A crash only your own mandatory post-change CTS sweep finds, not `check-feme`, is still your regression to fix before moving on

- `check-feme`'s lit/unit-test corpus has no case combining a direct
  (no-`InputAttachmentIndex`) depth *and* stencil subpass read with real
  indexed reads in the same module -- exactly the shape that exposed
  `ENV6(b)(1)`'s name-mangling collision (`L504`). A hand-written unit

## Centroid interpolation has two independent implementations that must be kept in lockstep

- `FragmentWrapper.cpp`'s `StageOpKind::InterpolateAtCentroid` case lowers
  the explicit `interpolateAtCentroid()` GLSL/SPIR-V builtin. A
  completely separate C++ rasterizer code path,
  `Executor.cpp`'s per-sample varying-interpolation loop's `IsCentroid`
  branch, independently handles an ordinary `centroid`-qualified
  push-model varying (`centroid in vec3 x;`). Neither calls the other;
  a fix to one alone can silently break `dEQP-VK.*multisample_
  interpolation.centroid_interpolation_consistency.*`, which directly
  checks that both agree (`interpolateAtCentroid(sampleVarying) ==
  centroidVarying` for identical underlying data). Found and fixed in
  `VulkanCTSReport.md`'s `L506`.
- Relatedly, a per-pass `Coverage[4]` bitmask that is deliberately
  narrowed to a single sample bit during forced per-sample shading
  (correct for `gl_SampleMaskIn`/`SV_Coverage`) is *not* safe to reuse
  for a centroid computation, which needs the whole pixel's coverage
  regardless of which single sample is currently being re-shaded. A
  `sample`-qualified varying's mere presence in a fragment shader forces
  per-sample shading of the *entire* shader, including any unrelated
  `interpolateAtCentroid()` call -- exactly `centroid_interpolation_
  consistency`'s own shape. When adding a new narrowed-per-pass ABI
  field, check whether any *other* consumer in the same struct actually
  needs the un-narrowed, whole-pixel version, rather than assuming one
  shared field serves every reader correctly.

## An `mlir-translate --deserialize-spirv` verifier failure through a lit `RUN` pipe can silently "pass" even when the diagnostic is real

When a FileCheck-based lit test pipes `mlir-translate`'s output straight
into `FileCheck` (e.g. `spirv-as ... | mlir-translate --deserialize-spirv
- -o - | FileCheck %s`), a genuine MLIR verifier failure in the
deserializer (emitted to stderr, not stdout, and causing an empty or
truncated stdout) does not reliably fail the lit test the way a direct,
un-piped invocation does -- confirmed while root-causing `VulkanCTSReport.
md`'s `L507`: deliberately reverting the fix and re-running the new
regression test via `llvm-lit` still reported `PASS`, even though the
exact same reverted binary, invoked directly as `mlir-translate
--deserialize-spirv t.spv -o -`, printed the real "branch has 0 operands
for successor #N, but target block has 1" verifier error to stderr and
nothing useful to stdout. Always confirm a new regression test's
"fails without the fix" half with a *direct* (non-piped, non-lit)
invocation of the tool, not just by running the lit test itself through
`git stash`/rebuild -- a passing lit test alone does not prove the test
is actually exercising the bug.

## When static trace/dump cross-referencing across multiple sessions is
## inconclusive, add temporary targeted debug prints in the suspect code
## path directly -- don't keep re-deriving from existing instrumentation

Two prior sessions investigating the same dominance bug
(`ENV6(c)(2)(h)`, `stable-mergesort-for-always-false-if-discard`) both
reasoned from `FEME_DEBUG_FLATTEN_TRACE=1`/`FEME_OPT_DUMP_INVALID=1`
output alone, cross-referencing block names and trace lines by hand
across several layers of recursive calls -- and both arrived at a
plausible but *wrong* call-chain attribution (blaming
`flattenLoopBodyRegion`/`flattenKnownDivergentBranch`, or a nested
recursive `flatten` call bounded by nothing, when the real call chain
was `LoopLinearizer::linearizeCycle`'s own loop-body fixed-point scan
calling `flattenLoopBodyDiamond` directly and in total isolation).
What finally broke the stalemate: adding new, temporary `errs()` debug
prints directly inside the suspect functions themselves (guarded by
new, scratch env vars, never committed), printing exactly the
values/predecessor-lists needed to confirm or refute each hypothesis
at the precise moment of the buggy query -- rather than continuing to
reason indirectly from existing trace output. This took one targeted
build-and-run cycle to settle definitively what two prior sessions of
careful static analysis had not. Lesson: once static trace/dump
cross-referencing stalls (especially across sessions, where a
plausible-sounding but unverified hypothesis can get carried forward
as fact), stop reasoning from existing instrumentation and add new,
temporary, narrowly-targeted prints in the actual suspect code instead
-- it is faster and far more reliable than another round of manual
cross-referencing. Always fully revert such temporary instrumentation
(diff against a pre-change backup) before committing the real fix.

## A `validate`/`flatten`-style region walk's own predecessor-ownership
## check must cover *every* plain pass-through block it walks through,
## not just the `CondBr`-rooted reconvergence points it stops at

`DiamondFlattener::validate`'s existing `R->hasNPredecessors(2)` check
only ever looks at a `CondBr`'s own *computed* reconvergence point --
it says nothing about an ordinary `UncondBr` pass-through block the
walk merely passes *through* on the way there. A sibling diamond's own
merge block can sit silently in the middle of such a walk, looking
like ordinary straight-line code, while secretly being reachable from
outside the region under validation -- producing `select`s built from
values that don't dominate that outside path. When adding or auditing
a region-boundary/ownership check in this kind of pass, make sure it
applies to every block the walk visits, not only the blocks it
terminates at.

## A `deqp-vk` case that hits `vkWaitForFences Timeout` can hang forever at process exit, *after* printing its own `Fail` result

- A shader with a genuine runtime infinite loop (not a compiler crash) reports
  `Vulkan::Calling vkWaitForFences Timeout` / `Fail (Fail)` on its own test
  line -- but the `deqp-vk` *process itself* can then hang indefinitely
  afterward, never reaching its own exit. Confirmed via a live
  `gdb -p <pid> -batch -ex "thread apply all bt"` attach: the main thread is
  stuck in `vkDestroyDevice` -> `Device::~Device()` ->
  `QueueExecutor::~QueueExecutor()`'s own `std::thread::join()`, waiting on
  worker threads still parked in `QueueExecutor::run()`'s own
  `pthread_cond_wait` -- they never wake up once the queue's last submission
  never retires.
- This means a `timeout <N> ./deqp-vk --deqp-case=<one case>` invocation is
  **not** actually safe against this failure mode: `timeout` only sends
  `SIGTERM`/`SIGKILL` after its own deadline, so it does eventually reap the
  process, but anyone instead watching for `deqp-vk` to exit on its own
  (e.g. naively polling `ps`, or trusting a bare, un-`timeout`-wrapped
  single-case run to finish once the result line prints) will wait forever.
  Always wrap a *solo* single-case re-verification run in `timeout`, even
  when the case is expected to complete quickly, and if a process is still
  alive well after its own result line already printed `Fail`/`Pass`, treat
  that as this hang (confirm with `gdb`'s own thread-apply-all-bt, not a
  longer wait) rather than assuming it is still legitimately working.
- Confirmed this session (`ENV6(c)(2)(k)`): `timeout -s KILL <N> ./deqp-vk
  --deqp-case=<one case>` does reliably reap the process on its own with no
  further manual intervention needed -- `SIGKILL` cannot be blocked or
  ignored even while the main thread is stuck inside the uninterruptible
  `QueueExecutor::~QueueExecutor()` `std::thread::join()` above. Plain
  `timeout` (no `-s KILL`) sends `SIGTERM` first, which this hang *can*
  swallow indefinitely since nothing in the stuck call chain checks for it;
  always pass `-s KILL` explicitly for this specific failure mode rather
  than relying on `timeout`'s own default signal.

## `feme-run` cannot drive a fragment-shader standalone repro; use a live, `gdb`-sampled `deqp-vk` attach instead for a runtime hang

- `feme-run` (the DXIL/compute JIT-dispatch tool) only ever supports a
  *compute* entry point (`feme-cpu-prepare: no compute entry point named
  ...` if the module has none) -- a fragment (or any other graphics) stage
  can only be executed through the full `Graphics::Executor`/
  `GraphicsPipeline` path, which only a real Vulkan device (`deqp-vk`
  itself, or a hand-rolled driver-level harness) drives. There is no
  standalone, non-`deqp-vk` way to execute a fragment shader's generated
  code today. When a runtime hang's shader is a fragment shader, a safe
  *live* `deqp-vk` attach (see the `timeout -s KILL` entry above for why
  this is safe) is the only practical repro, not a `feme-run`-based one.
- When attached to a hanging `deqp-vk` process with multiple threads, a
  plain `gdb -p <pid> -batch -ex "thread apply all bt"` can mislead: once
  the shader's own JIT-compiled native code is genuinely spinning, that
  thread's backtrace is frequently unreadable (`Backtrace stopped: Cannot
  access memory at address ...`), because JIT-generated code has no CFI/
  unwind info for `gdb` to walk past frame 0 -- it is easy to instead focus
  on a *different*, merely-idle thread (e.g. a `QueueExecutor` worker
  parked in `pthread_cond_wait`, or the main thread legitimately blocked in
  `vkWaitForFences`) whose backtrace looks complete and plausible, and
  wrongly conclude the hang is there. Always cross-check with
  `ps -L -o pid,lwp,pcpu,stat,comm -p <pid>` first to find the one thread
  actually burning CPU (`%CPU` near 100, `STAT` `R`), then `gdb`'s own
  `thread <N>` (matched to that LWP via `info threads`) to inspect only
  that thread.
- Once on the right thread, a garbled/absent backtrace does not block
  useful diagnosis: `info registers pc`, `x/<n>i $pc-<k>` (disassemble
  around the live PC), and `info registers x30` (the link register, giving
  the caller's return address even with zero stack unwind support) can
  still identify what the spinning code is doing. Setting a breakpoint at
  a specific address seen in that disassembly and sampling general-purpose
  registers (`info registers`) across several hits is an effective way to
  check whether a suspected loop-carried value (e.g. an induction variable)
  is actually changing across iterations, without needing symbols or
  unwind info at all -- this is exactly how `ENV6(c)(2)(k)`'s root cause
  (a loop induction-variable register pinned at a stale value) was found
  this session.

## `FEME_DUMP_IR_POSTOPT=1` is the authoritative dump for codegen-level bug hunting, not `FEME_DUMP_IR_PRELINEARIZE=1`

- `feme/lib/Target/CPU/CompiledStage.cpp` supports several `FEME_DUMP_IR_*`
  env vars at different pipeline points. `FEME_DUMP_IR_PRELINEARIZE=1` (the
  one most sessions have reached for first) dumps IR *before*
  `libFeMeRuntimeCPU` bitcode linking and before the full optimizer
  pipeline runs -- it is useful for `Linearize`/`SIMDize`-stage work, but it
  is **not representative of what the backend (`llc`-equivalent CodeGen)
  actually compiles**: `feme.cpu.resource.load.raw.*` calls are still
  external declarations at that point, and none of the post-link
  optimizations (inlining, DCE, SimplifyCFG, etc.) have run yet.
- For any investigation suspecting a CodeGen (register allocation,
  scheduling, instruction selection) bug rather than an IR-generation bug,
  use `FEME_DUMP_IR_POSTOPT=1` instead -- it dumps immediately before
  codegen, *after* linking in the real `libFeMeRuntimeCPU` function bodies
  and *after* `OptimizerPipeline().run()`. This is the true, authoritative
  ground truth for what the backend receives, and is the only dump that
  should be used to decide whether a bug is in the middle end (IR-level,
  still visible/fixable via `opt`-equivalent passes) or in CodeGen
  (register allocation/scheduling/MC emission, only visible via
  `llc -print-after=...` or later).
- The dump output concatenates one `Module::print()` call per shader stage
  compiled in the same process (e.g. vertex then fragment) into a single
  log file, and **both modules reuse the same function names** (e.g.
  `feme_cpu_entry_main` appears twice). Treating the whole file as one
  module will not parse correctly in `opt`/`llc` (duplicate symbol
  errors) -- manually slice the file at the boundary of the *second*
  `define void @feme_cpu_entry_main` (or whichever entry point repeats) to
  get one standalone, parseable module per stage.
- A static `llc -O2` compile of a module extracted this way is a faithful
  stand-in for the real JIT's output, not just a rough approximation: the
  FeMe JIT's `TargetMachine` is created with empty `CPU`/`Features`
  strings (see `feme/lib/Target/TargetMachineBackend.cpp`), identical to
  invoking plain `llc` with no `-mcpu`/`-mattr` flags -- there is no
  target-config mismatch to account for when comparing static `llc` output
  against live JIT-compiled code's disassembly.
- When correlating a live register sample (via `gdb`-attach to a hung JIT
  process) against statically-reconstructed IR/MIR, do not assume a
  register observed via `cmp`/compare instructions is the loop's own
  induction variable just because the comparison "looks right" -- a
  loop-invariant bound hoisted into the preheader (e.g. loaded once from a
  uniform buffer before the loop) can be compared against a *different*,
  freshly-computed register every iteration, producing an identical
  surface pattern (`cmp <fixed>, <fresh>`) to a genuinely-unthreaded
  induction variable. Always cross-check *which* operand of the comparison
  changes across loop-trip samples, not just that *a* comparison exists at
  the expected source location, and verify against the actual generated
  assembly (not just the pre-RA MIR) which register is the preheader-hoisted
  constant and which is the per-iteration value, before concluding a
  register is "stuck" due to a bug rather than by design (e.g. a
  correctly mask-gated `csel`/`select` deliberately freezing a value once
  that lane's own iteration condition becomes inactive).

## Investigating a `Linearize`/`SIMDize` IR-correctness bug: prefer `feme-opt` + pre-Linearize dumps over post-opt IR, assembly, or live-process debugging

- For any suspected masking-correctness bug in `feme-cpu-linearize`/
  `feme-cpu-simdize` (not a CodeGen/register-allocation bug), the fastest
  and most reliable methodology, in order:
  1. Capture the real shader's pre-Linearize IR with
     `FEME_DUMP_IR_PRELINEARIZE=1` under a bounded `timeout -s KILL` (safe
     even for a case that hangs at *runtime*, since the hang only manifests
     much later than IR dumping) and extract the relevant function's
     module.
  2. Run `feme-opt --llvm -passes=feme-cpu-linearize -S <file>.ll` on that
     extracted module -- this runs *just* the Linearize pass standalone,
     with no `deqp-vk`/Vulkan pipeline dependency at all, and is
     dramatically faster/safer than live-process debugging for any
     control-flow/masking question.
  3. Add `FEME_DEBUG_LINEARIZE_TRACE=1` to the same invocation to print each
     recognized cycle's actual `Header`/`Latch`/`ExitBlock` names and
     `HeaderDivergent`/`LatchDivergent` classification directly -- this is
     ground truth for which blocks the pass itself reasons about.
  4. Only fall back to post-opt IR (`FEME_DUMP_IR_POSTOPT=1`), assembly, or
     live-process/`gdb`-attach debugging for a question that is genuinely a
     later-pipeline-stage (CodeGen/register-allocation) concern, not a
     Linearize/SIMDize masking-correctness one.
- Block names seen in post-opt dumps (`FEME_DUMP_IR_POSTOPT=1`) or final
  disassembly do **not** reliably correspond to the `Header`/`Latch`/
  `ExitBlock` identities Linearize itself reasoned about -- later generic
  LLVM passes can rename/restructure blocks after Linearize runs. Inferring
  cycle structure from post-opt block names/numbers (rather than from
  `FEME_DEBUG_LINEARIZE_TRACE=1`'s own direct output) is a recurring trap
  that has cost multiple sessions of mis-directed investigation.
- When constructing a synthetic lit-test repro of a
  `collectUniformPassThroughRegion`-triggering shape (a `BodyRegion` block
  with its own direct, `Latch`-bypassing edge to the cycle's `ExitBlock`):
  that bypass block's own branch condition must be genuinely **uniform**
  (e.g. compared against a constant), not thread-id-derived/divergent -- a
  divergent bypass condition causes the whole region to be rejected or
  handled completely differently, and will silently fail to reproduce the
  intended shape at all.

## Diagnosing a silent, no-diagnostic all-black-render `Fail`: bisect the pipeline stage-by-stage, and suspect poison

- A real shader whose entry function silently loses its whole body (ends up
  as `{ ret void }`/`unreachable` with no IR verifier failure and no
  `FEME_VULKAN_LOG_CREATION_ERRORS=1` diagnostic) is a strong signal of a
  **poison value reaching a branch condition**, not a missing feature or a
  genuinely malformed-IR bug. LLVM's optimizer (`InstCombine`/
  `SimplifyCFG`) is legally entitled to delete anything reachable only
  through a branch on a poisoned condition -- this is valid per the
  LangRef, produces no diagnostic anywhere, and can happen inside any pass
  that runs ordinary cleanup optimizations, not just an obviously
  "optimizing" one (`UnrollConstantTripCountStageLoopsPass` runs its own
  `InstCombinePass`/`SimplifyCFGPass` unconditionally on every graphics
  entry function, including ones with no loops at all, purely for
  legitimate post-unroll cleanup -- it is a generic "detector"/"amplifier"
  of a poison bug introduced earlier in the pipeline, not itself buggy).
- The most likely *source* of such a poison value in a SPIR-V-to-LLVM
  lowering: any op whose SPIR-V spec permits an out-of-range operand with
  an "undefined result" (an unspecified-but-defined value, analogous to
  LLVM's own `undef`) that gets lowered directly into an LLVM instruction
  with a *stronger* UB-carrying precondition (e.g. `BitField*`'s `Offset`,
  or a plain shift op's `Shift`, both of which the SPIR-V spec allows
  `>= Size`, feeding directly into `llvm.lshr`/`llvm.shl`/`llvm.ashr`'s
  shift-amount operand, which the LLVM LangRef says is outright *poison*
  once out of range). Any such site should clamp the operand to the
  LLVM instruction's own valid range (e.g. via `llvm.intr.umin`) *before*
  using it, rather than passing it through unclamped and relying on the
  SPIR-V spec's weaker guarantee to somehow carry over.
- To localize *which* pass actually erases such a body (when the bug is in
  the real `feme_vulkan` driver pipeline, not a standalone `feme-opt`
  pass), bisect stage-by-stage with temporary, env-var-gated
  `module.print()` dumps inserted directly in the C++ driver code
  (`Pipeline.cpp`/`GraphicsPipeline.cpp`) at each pass boundary -- the
  pre-existing dump points (`FEME_DUMP_IR_PRESPIRV`/`PRECANON`/`POSTCANON`/
  `PRENORM`/`PRELINEARIZE`/`PRESIMD`) do not cover every pass boundary, and
  guessing the culprit pass from code-reading alone is unreliable (an
  `eraseUnreachableBlocks` hypothesis looked very plausible but was wrong).
  Remove these temporary dump points before committing once the bisection
  is done -- they are single-use triage aids, not a permanent part of the
  pipeline's debug surface.
- A standalone `feme-opt --feme-convert-spirv-to-llvm` repro of one pass
  succeeding does **not** prove the full real pipeline is correct: the real
  driver runs several more passes afterward
  (`patchUnboundedResourceRanges`, `InlineHelperFunctionsPass`,
  `UnrollConstantTripCountStageLoopsPass`, `CanonicalizeStagePass`, ...)
  that a single-pass `feme-opt` invocation does not exercise at all. Always
  cross-check a standalone-pass fix against a real `deqp-vk` re-run before
  trusting it.

## `Linearize.cpp` promoted-Latch general-fallback masking path gotchas (found investigating `ENV6(c)(2)(a)`)

- `linearizeCycle`'s "general fallback" masking path (reached whenever a
  cycle's own `Latch` was promoted from a trivial relay stub,
  `LatchWasPromoted`, which explicitly excludes the correct
  `flattenLoopBodyRegion`-based branch -- see that guard's own comment,
  `K6v`) did not originally route its own body region through
  `DiamondFlattener` at all, just a naive flat per-block masking walk.
  Any uniform diamond sitting directly in this path's own body region
  (e.g. a `discard`-guard `if`/`else` reconverging before `Latch`) had its
  mask-narrowing effect applied unconditionally to the *whole* shared
  mask, not just its own arm -- a `discard` in only one arm permanently
  corrupted the loop's mask to a compile-time-constant `false` even when
  that arm could never actually be taken for the real shader's inputs.
  When adding any new masking logic to this fallback path, always
  consider whether `DiamondFlattener::flattenLoopBodyRegion` (already
  proven correct by the sibling non-promoted-latch branch) should be tried
  first, falling back to the naive walk only when it declines.
- `freezeLoopCarriedValues`'s `BodyMask` parameter is documented as
  "whether this specific wide iteration was a real one for a given lane"
  -- but a cycle's own `Latch` can have **two independent** conditions
  that gate a lane's continued participation: a divergent, mask-
  affecting-op-driven liveness (`MasksAtLatch.Live`) and a separate,
  genuinely uniform natural trip-count condition (`closeLatch`'s own
  `NaturalContinue`). If a loop's liveness mask happens to never actually
  narrow (e.g. a `discard` that is reachable in the IR but never fires for
  the real inputs), feeding `BodyMask` only the liveness mask leaves it
  constant-`true` for the loop's whole run, so any loop-carried freeze
  gated on it keeps selecting the *next* round's incoming value even on
  the round whose own uniform trip-count check is what actually ended the
  loop -- an off-by-one that only shows up in values read *after* the
  loop exits. Any caller of `freezeLoopCarriedValues` must pass the
  **combined** condition (liveness AND natural-continue), not raw
  liveness alone, whenever `Latch` has its own separate natural branch.
  `closeLatch`'s own `OutPerLaneContinue` out-parameter computes this
  combined, per-lane-shaped value before the group-wide
  `createUniformMaskAny` reduction that the scalar `Continue` return value
  needs -- use it rather than re-deriving the combination at each call
  site.

## A silent all-black render can originate from an upstream MLIR dialect *fold*, not just a FeMe pass -- `--debug-only=dialect-conversion` tells fold vs. pattern apart

Investigating `ENV6(c)(2)(n)` (`cov-nested-structs-function-set-inner-struct-field-return`),
the usual `FEME_DUMP_IR_PRESPIRV`-vs-later-dump bisection (see the
"Diagnosing a silent, no-diagnostic all-black-render `Fail`" lesson above)
showed the corruption was *already present* in the very first post-translate
dump, before any FeMe pass ran at all -- i.e. during SPIR-V-to-LLVM-dialect
conversion itself. That conversion is driven by MLIR's own dialect
conversion framework, which runs both FeMe's registered conversion
*patterns* and each source dialect's own op-local `fold()` methods as part
of legalization; a bug can live in either.

- To tell them apart without a full `deqp-vk` run: extract the broken
  function's SPIR-V-dialect MLIR from a `FEME_DUMP_IR_PRESPIRV=1` dump into
  a standalone `.mlir` file (strip any `//` line comments first -- they can
  break reparsing of printed block-argument-list syntax), then run
  `feme-opt --feme-convert-spirv-to-llvm /path/to/file.mlir
  --debug-only=dialect-conversion`. A `"* Fold {...} -> SUCCESS"` line in
  the trace means a dialect `fold()` is responsible, not a conversion
  pattern -- don't assume the bug must be in a FeMe-authored pattern just
  because the corruption appears mid-conversion.
- Once a `fold()` is implicated, reproduce it with **zero FeMe code**
  by hand-writing a minimal pure-source-dialect `.mlir` snippet and running
  it through plain upstream `mlir-opt --canonicalize` (not `feme-opt`).
  This both confirms the bug is a genuine upstream defect (not an artifact
  of FeMe's own conversion setup) and gives the smallest possible
  reproducer for the eventual lit test.
- Concretely: `mlir::spirv::CompositeExtractOp::fold`
  (`mlir/lib/Dialect/SPIRV/IR/SPIRVCanonicalization.cpp`) only checked for
  an *exact* index-list match against a feeding `CompositeInsertOp`; on any
  mismatch it unconditionally walked past the insert, silently discarding
  it whenever the two index lists merely overlapped (one a strict prefix
  of the other) instead of being identical or fully disjoint -- the same
  "extract reads a shallower path that the insert's deeper path also lies
  under" bug pattern the LLVM dialect's own (correct) `fold` for
  `llvm.extractvalue` already guards against via its 3-case exact/prefix-
  descend/prefix-stop classification. Fixed by porting that same
  classification into the SPIR-V dialect's fold (upstream MLIR commit,
  outside `feme/`, per the standing "issue outside FeMe" protocol).

## Re-verify a case's actual current symptom before trusting a roadmap entry's stale description -- an earlier session's fix elsewhere can silently change it

`ENV6(c)(2)(m)`'s roadmap entry described `cov-two-nested-loops-switch-case-matrix-array-increment` as a runtime hang (`vkWaitForFences Timeout`), discovered during an earlier session's full-corpus re-run. By the time this session picked it up, two intervening sessions (`ENV6(c)(2)(a)` remainder, `ENV6(c)(2)(n)`) had landed unrelated `Linearize.cpp`/upstream-MLIR fixes that changed this case's own codegen enough to make it fail at an *earlier* point -- a fast (~0.1s), deterministic, compile-time "unsupported" diagnostic, not a hang at all. Always re-run the actual `deqp-vk` case fresh (with a short, safe timeout the first time) before assuming a roadmap entry's documented symptom -- hang vs. crash vs. clean diagnostic vs. silent wrong-render -- still describes current behavior; an unrelated fix elsewhere in the same pipeline can move a case to a completely different, often much safer, failure mode without anyone noticing until the next session that actually re-investigates it.
